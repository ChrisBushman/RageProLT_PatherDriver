# Sleep / wake (checklist B2): stock behaviour, risks, proposed implementation and test plan (Nov 26)

Status: investigation and proposal only; nothing implemented, nothing run on the G4 (read-only pulls of `IOGraphicsFamily`, `IONDRVSupport`, `IOPCIFamily`, `IOFramebuffer.h` and `/usr/bin/pmset` from the MDD's Panther install, kept in the scratchpad). Evidence levels: "static" = read from disassembly or a header; "inferred" = reasoning from static facts; "not established" = no evidence. Addresses: stock `ATIRagePro.kext` md5 8fc97891 (`__text` file offset = vaddr + 0x33c), `IOGraphicsFamily` / `IONDRVSupport` 10.3.9 `__text` addresses, NDRV Ghidra image addresses (`ATY,264LTPro`, as in apple-ndrv-framebuffer.md).

## 1. Short answers

1. **Stock saves and restores no chip state at all.** `system_will_sleep` / `system_did_wake` only flip a user-mapping redirect; the real work is the same path as a display mode change (drain, evict textures, reset the VRAM heap, stop the engine; on wake re-run `initialize_hardware`: engine reset + re-read of the CRTC). Chip state (CRTC, DAC, PLL, FIFO, memory, bus control) is the **framebuffer's** job (the NDRV), and the NDRV on wake only pulses two memory resets and restores a few registers.
2. **The notifications our kext needs are framebuffer notifications, not IOService power callbacks.** Stock registers no PM (`joinPMtree`/`PMinit`/`registerPowerDriver` appear in the stock kext only as vtable-inheritance imports, no call sites). Our kext already subscribes to the same notifications, but it maps the *info == 0* sleep/wake events to mode change and **ignores the info != 0 events** (system sleep proper), and it has **no gate** that stops chip access while the chip is suspended.
3. **Risk that the NDRV wake overwrites our BUS_CNTL / memory settings: low on the decoded path.** The wake path writes none of BUS_CNTL, MEM_CNTL (timing), MEM_BUF_CNTL, DAC/PLL/CRTC (in the fast path). It pulses `EXT_MEM_CNTL` reset bits and `GEN_TEST_CNTL` bit 9 (memory-controller reset). The BUS_CNTL write constant (0x7b33a040) is in the chip-init function, which is not on the wake path. Not every callee of the wake function was traced (list in section 4), so this is "low", not "excluded". The bigger hazard is the opposite: **reading a suspended or un-POSTed chip blocks the CPU forever.**
4. **On the G4 rig the framebuffer side of sleep does not exist.** `RageStubFB` never registers with power management and never calls `handleEvent`; static reading of `IOFramebuffer` says its sleep notifications are only produced for a framebuffer that does (inferred, section 5). Real system sleep on the MDD with a PC Rage card is a hazard (the card may lose power and then hang the first register read), so it needs a staged protocol (section 8). What *can* be tested without risk: the kext's event state machine and gating, driven by notifications the stub emits itself.
5. Panther's `pmset` has **no `sleepnow`/`displaysleepnow`** (string search of `/usr/bin/pmset` on the MDD: only dim/sleep/spindown timers). Sleep must be triggered by an idle timer (`pmset sleep N`), the Apple menu, or `osascript -e 'tell application "Finder" to sleep'` (osascript exists), from the logged-in GUI session.

## 2. How a sleep reaches an accelerator on Panther (static)

### 2.1 `IOFramebuffer` (IOGraphicsFamily) side

- Event numbers (`IOFramebuffer.h`, 10.3.9): 1 DisplayModeWillChange, 2 DisplayModeDidChange, 3 WillSleep, 4 DidWake, 5 DidPowerOff, 6 WillPowerOn, 7 WillPowerOff, 8 DidPowerOn, 9/10 Will/DidChangeSpeed. The header documents `handleEvent` as the subclass's call for 7 and 8 ("call before entering a state other than the maximum" / "after entering the maximum power state"; "none of the above events require additional info, pass zero").
- `IOFramebuffer::handleEvent(event, info)` (0xbe88): event 7 -> deliver 7; event 8 -> deliver 8, then, once per cycle (guarded by flag `this[0xe4] & 0x40000`, a global at TOC -0x22fc and the fields `this[0xac]` / `this[0x11c][0xfe]`, whose meanings are not identified), deliver event **1 (info 0)** and then event **4 (info as given, 0 here)**. Called with event **4 and info != 0** (the NDRV's wake call) it first copies the screen image saved by `checkPowerWork` back into VRAM and frees it (IOGraphics writes VRAM at that point, so the chip is already up), then delivers the event. Other events are forwarded unchanged.
- `IOFramebuffer::checkPowerWork` (0xc43c): when the flag `0x40000` is set (the framebuffer was previously woken through the pair above) and power is going down, it delivers **event 3 with info 0** (WillSleep), then (if the framebuffer answers the private attribute `'vrsv'`, 0x76727376) **saves the visible frame into pageable memory** (`IOMallocPageable`, copy, `vm_map_wire`) so IOGraphics, not the driver, restores the screen; then it calls `setAttribute('powr', state)` (0x706f7772) on the subclass.
- Nothing in `IOGraphicsFamily`' `__text` calls `PMinit`, `joinPMtree` or `registerPowerDriver` (relocation scan of the whole text): a framebuffer subclass must register itself for power management and call `handleEvent`. `IONDRVFramebuffer` does (`initForPM` 0x7744, `ndrvSetPowerState` 0x7b10, `ndrvUpdatePowerState` 0x7a1c).

### 2.2 `IONDRVFramebuffer::ndrvSetPowerState(state)` (IONDRVSupport 0x7b10), what the Lombard's framebuffer does

States 0..2 (anything above is clamped to 2). In order:
1. Leaving state 2: `handleEvent(7, 0)` then the NDRV's own display-off step; the end-of-function event will be 5 (DidPowerOff). Entering state 2: `handleEvent(6, 0)`; end event 8.
2. **Entering state 0:** wait up to 200 ms for the display, then `redirect(kernel_task, true)` on the descriptor returned by vslot 0x5d0 (the VRAM range, `getVRAMRange`; all *user* mappings of VRAM are redirected so a user process cannot touch a powered-down chip), then **`handleEvent(3, info = 1)`**: WillSleep with a **non-zero info**.
3. The NDRV control 0x19 (sleep/wake request; NDRV `FUN_1000e280`, section 4) performs the chip suspend or wake.
4. **Leaving state 0:** `redirect(kernel_task, false)`, then **`handleEvent(4, info = 1)`**: DidWake, non-zero info, *after* the chip wake control.
5. The end event (5 or 8, info 0) is delivered last; event 8 makes `IOFramebuffer` add the (1,0) and (4,0) pair of 2.1.

So on a Lombard an accelerator can see, in some order, both "info == 0" events (from `IOFramebuffer`: (3,0) before the VRAM save, (1,0)+(4,0) after power-on) and "info != 0" events (from the NDRV: (3,1) before chip suspend, (4,1) after chip wake). Exact interleaving across a display-only sleep versus a system sleep is **not established** (it depends on which power state IODisplayWrangler asks for; state 0 appears to be the one that carries the (3,1)/(4,1) pair, and display sleep may use it too).

### 2.3 Stock accelerator: what each event does (static)

`IOATIRProAccelerator::display_change_handler` (0x20c; registered per framebuffer by `foundFramebuffer`, 0x398, with `IOFramebuffer::addFramebufferNotification`; jump table at 0x254):

| event | info | action (vslot of `ATIRagePro`) |
|---|---|---|
| 1 | any | `OSIncrementAtomic(this+0xc4)`; first -> 0x578 `display_mode_will_change(event)` |
| 2 | any | `OSDecrementAtomic`; last (old value 1) -> 0x57c `display_mode_did_change()` |
| 3 | 0 | same as 1 (event number 3 is passed, `disp_mode_will_change` stores `this[0x7d] = (arg == 3)`) |
| 3 | != 0 | 0x580 `IOATIRProAccelerator::system_will_sleep` |
| 4 | 0 | same as 2 |
| 4 | != 0 | 0x584 `system_did_wake` |
| 5-8 | - | ignored (jump table default) |
| 9 / 10 | - | 0x588 / 0x58c `system_will/did_change_speed` (both are a bare `blr` in `ATIRagePro`: 0x1346c, 0x13470) |
Before dispatch the handler refreshes the record's VRAM map (0x4288: `getVRAMRange()->map(0x101)`).

- `system_will_sleep` (0x4aa0) and `system_did_wake` (0x4b38), full semantics: `mutex_lock(this[0x544])`; will: `if (!this[0x7f]) { if (this[0xa8]) this[0xa8]->redirect(kernel_task, true); this[0x7f] = 1; }`; did: `if (this[0x7f]) { if (this[0xa8]) this[0xa8]->redirect(kernel_task, false); this[0x7f] = 0; }`; `mutex_unlock`. `this[0xa8]` is the provider's device memory of config register 0x18 (BAR2, the 4 KB register block), falling back to 0x10 (BAR0), set in `ATIRagePro::start` (0x11fc4-0x12014); by constant only, the accessor identity is inferred. **That is all**: no register is read or written, no engine drain. The purpose is to make every *user-task* mapping of the chip's registers (stock clients map registers into the process) harmless while the chip is down.
- `display_mode_will_change` (0x1290c) and `display_mode_did_change` (0x12aa8): detailed in `display-mode-change.md`. Relevant to sleep: will = drain (`waitForTimeStamp`), release AGP memory, evict every texture, move every surface buffer to backing store, **reset the whole VRAM heap** (`init_pool(0)`), `stop_engine`, redirect `this[0x548]` (the VRAM/aperture descriptor); did = `initialize_hardware` then `reset_access`, commit AGP, un-redirect.
- `initialize_hardware` (0x12888) = `reset_GUI` (0x12ff4) + `set_display_mode_and_vram` + `this[0x7c] = 1` + `submit_empty_buffer`. `reset_GUI` writes only engine-side registers (static, from the `lwbrx/stwbrx` offsets): `GEN_TEST_CNTL` byte 1 bit 0 (GUI_RESETB) pulse (offset 0xd0), FIFO/GUI-status related offsets 0x310/0x338, scissor registers (0x2a0-0x2b0 set to 0x3fff/0xfff), destination/source offset-pitch (0x100/0x180) copied from CRTC_OFF_PITCH (0x14), a few engine setup words (0x2c8/0x2d0/0x300-0x308/0x130/0x1b4). It does **not** write BUS_CNTL, MEM_CNTL or any display register; `set_display_mode_and_vram` **reads** CRTC registers (0x00, 0x08, 0x1c, 0x5c) and MEM_CNTL (swap mode) and sets/clears one bit of register 0xa8 around the read (LCD_DATA by the NDRV's map; purpose not decoded).
- Net: stock treats sleep exactly like a mode change plus a user-mapping redirect; it keeps no shadow copy of chip registers and never restores any.

## 3. What our kext does today

- `RageLTMode.cpp::fbEvent` (line 62-70): `will = (event == WillChange) || (event == WillSleep && !info)`, `did = (event == DidChange) || (event == DidWake && !info)`; counter `fModeDepth`; first will -> `modeWillChange()`, last did -> `modeDidChange()`. **Events with info != 0 fall through and are ignored; 5-8, 9, 10 are ignored** (same as stock for 5-10).
- `modeWillChange` (line 71-87): bump `fModeGen` (odd), disable the overlay, drain (`idleWait`), invalidate every context's target/Z, unreserve the display blocks. `modeDidChange` (89-100): read BUS_CNTL, set `BUS_EXT_REG_EN` (bit 27) if clear, `fEngineLive = false`, `engineEnable()` (checks BUS_CNTL bit 27 and CRTC_GEN_CNTL bit 25, resets the engine, re-inits the context), `reserveDisplay()` (re-reads the CRTC), bump `fModeGen` (even). The GL bundle drops every cached offset and re-uploads textures when it sees the generation change (`gld_core.c: mach64_mode_check`, `mach64_tex_invalidate_all`).
- There is no `RageLTPower`, no `PMinit`, no `setPowerState`, no thread, timer or interrupt in the kext (grep: none), so nothing polls the chip in the background; every chip access is on a client or notifier call path.
- **Gating audit** (functions in `kext/*.cpp` that touch registers or the VRAM aperture, whether they refuse while `fModeGen` is odd; callers may gate higher up, this is the function body only): gated: `submitBatch`, `clearZ`, `fillRect`, `setRenderTarget`, `presentEx`, `swapTarget`. **Not gated in the function itself:** `vramCopyIn`, `vramCopyOut`, `scanoutCopyOut`, `xferKick`, `xferWait`, `dmaSubmit`, `dmaWait`, `waitFence`, `ovlOn`, `ovlFlip`, `ovlB0`, `regDump`, `modeRegsRead`, `engineSelfTest`, the GL client's first-open read. `vramCopyIn/Out` call `idleWait()` and then read or write the aperture: during a sleep these would touch a suspended chip. During a plain mode change the chip is live, so the missing gate is a correctness gap, not a hang; during a sleep it is a hang risk.
- PCI side: `RageLTDevice::start` enables memory decode only; the DMA path checks `BUS_CNTL` and the PCI command register (event 0xd0073000 logs `configRead32(kIOPCIConfigCommand)`), falling back to the CPU path on surprises. Bus-master enable is set per operation and `BUS_CNTL` restored as found (design 11.16, `texture-dma-upload-standalone.md`); the only persistent write is `BUS_EXT_REG_EN`.

## 4. The NDRV's sleep / wake path, decoded further (refines apple-ndrv-framebuffer.md 17.6)

`FUN_1000e280` (control 0x19; `*param_1` = new sleep state, `my_count` nests requests). New decode:
- **Sleep** (state 0): saves the connection signature (my_display/sense bytes, `0x1ad78-0x1ad7e`, and `CRTC_INT_CNTL` into `_DAT_1001ad74`); if the chip is not already in a PM state (POWER_MANAGEMENT byte 3 bits 7:6 == 0) turns the three outputs off (LCD `0x1000a380`, CRT `0x1000a660`, TV `0x1000a7d0`, `my_lcd/my_crtc/my_tv`); when the count reaches zero: **writes register 0x78 = 0xfbff0000**, saves and clears CRTC_INT_CNTL (0x18), waits 20 ms, enters suspend (`0x1000a9a0(2)`).
- **Register 0x78 is `GP_IO`** (RRG offset 0_1E = byte 0x78; same mapping as `ddc-edid-probe.md`): the value 0xfbff0000 = direction bits 31:16 mostly output (all but bit 26) with all output levels 0. It is the board-level GPIO sequencing the panel/backlight/PHY on the Lombard (which pins do what is not established); apple-ndrv-framebuffer.md 17.6 and vblank.md say "register 0x78 was not identified": that gap is closed here (identification by register map, function by inference only).
- **Wake** (when POWER_MANAGEMENT status bits say the chip was in a PM state): `0x1000a9a0(3)` (leave suspend, 500 ms), then `0x10015130` and `0x10015210`, then restore register 0x18, clear a DAC power-down bit, re-probe monitors, recompute heads, compare the connection signature.
  - **`0x10015130` is the documented SDRAM reset pulse**: byte 0xac = `EXT_MEM_CNTL` bits 3:0 read-modify-write: `|2` (MEM_SDRAM_RESET = 1), `|0xa`, `|0xe` (MEM_CYC_TEST = 10 then 11), 10 us delay, `&0xf3|2` (CYC_TEST = 00), `&0xf1` (RESET = 0). This is exactly RRG EXT_MEM_CNTL's "In order to reset SDRAM" sequence (steps 1-5, RRG p. 4-15). It touches only the low nibble of that byte.
  - **`0x10015210` is a memory-controller reset pulse**: `GEN_TEST_CNTL` (offset 0xd0) bit 9 cleared, set, 10 us, cleared. RRG: bit 9 `GEN_SOFT_RESET` = "Reset the memory controller".
  - So the NDRV's "chip init helpers" on wake are **memory bring-up pulses, not register-file re-initialisation**. They are consistent with VRAM contents being lost or the SDRAM state machine needing re-initialisation after suspend, and with all other chip registers being **retained** (the fast path, signature unchanged, re-programs no CRTC/DAC/PLL/FIFO/bus register: inferred from absence in the decoded code).
  - Identical signature -> fast path (no mode set). Different (monitor plugged/unplugged during sleep, lid) -> `0x100073b0` (decoded: it maps the monitor sense bytes to a mode id via the 0x1d-entry table at `0x1001c168`, it is **not itself a mode set**; correction to 17.6), then `VSLDoInterruptService(this[0x5c8])`, i.e. it pokes the connect-change interrupt service so IOKit re-probes and issues a mode change (events 1/2 to us).
- **Where BUS_CNTL is written:** `FUN_10016d80` (BUS_CNTL = 0x7b33a040, DAC_CNTL, HW_DEBUG, CUSTOM_MACRO_CNTL; called from the chip init at funcs.c line 7290 and `FUN_1000d2f0`, which also moves BAR2/sets cache modes) and `FUN_100015a0` (engine reset: GEN_TEST_CNTL GUI_RESETB toggles, then `BUS_CNTL |= 0x800000`; reached through `FUN_10001710`; its callers on the wake path were not traced). 0x7b33a040 has bit 27 (BUS_EXT_REG_EN) set, bit 6 (bus-master disable per the atyfb header, unproven, see 12 in the NDRV doc) set.
- **Callees of the wake path NOT decoded** (so "no BUS_CNTL write on wake" is a statement about the decoded part only): `0x1000b5e0` (monitor probe), `0x1000bc70` (head routing), `0x1000be30`, `0x1000b730`, `0x10008180`, `0x1000c0d0`, `0x10007210`, `0x1000cc60`, `0x10007b40`, `0x1000a9a0` (power state machine; its register writes are LCD/PM-domain, decoded in 17.6).

## 5. Risks, ranked

1. **Chip access while the chip is suspended or powered down (hang).** The ledger lesson (memory-map.md 6): a PPC read to an un-clocked/un-initialised chip blocks the CPU forever, no PCI timeout. After `(3, info=1)` the NDRV suspends the chip; an in-flight client call, a fence poll or a `vramCopyOut` in that window hangs the machine. Mitigation: a single "chip may be touched" gate checked under `fLock` at the top of every function listed as ungated in section 3, set closed on the first will-event (info 0 or 1) and opened only after the wake verification (section 6, step 4). The order matters: stock's notifications arrive before the NDRV suspends the chip ((3,0) from `checkPowerWork` precedes `setAttribute('powr')`; (3,1) precedes control 0x19), and (4,1) arrives after the NDRV's wake control, so a kext that quiesces on the first will and resumes on the last did never reads a suspended chip, *provided those events are delivered*.
2. **Unmatched pairs.** The counter `fModeDepth` pairs will/did. Stock has the same counter. If a will arrives and its did never does (the G4 stub emits none; an NDRV path that skips one), `fModeGen` stays odd and every client call returns NotReady forever. Mitigation: pair info != 0 events on a separate counter/flag (idempotent: will sets, did clears, like stock's `this[0x7f]`), and a log line when a did arrives without a will.
3. **VRAM contents after wake: assume lost.** The NDRV's SDRAM reset on wake and IOGraphics' own screen-image save (`'vrsv'`) both suggest it. Our treatment is already right if the generation mechanism fires: all render targets, Z and textures are invalidated and re-created by the bundle. Not established whether the Lombard's VRAM actually decays (SELF_REFRESH/TRISTATE_MEM_EN were set at init, 17.3); a canary test on the G4 can only answer it for the MDD slot.
4. **PCI config space.** `IOPCIDevice::setPowerState` (IOPCIFamily 0x4ea4) saves (state 0, via the bridge) and restores (states 1/2) config space and writes the PCI PM capability when present; whether our card's nub goes through state 0 on this machine is not established. A wake verify must read the PCI command register and BAR0 (config reads cannot hang) and repair memory-decode / bus-master bits it finds clear (the DMA path needs bus mastering).
5. **NDRV wake overwriting our state.** Section 4: it does not touch BUS_CNTL/MEM_CNTL on the decoded path; the memory-controller reset might reset registers inside the controller (not documented which); our kext writes none of MEM_CNTL/EXT_MEM_CNTL/MEM_BUF_CNTL (grep), so there is nothing of ours to lose there. What we own and may lose: `BUS_EXT_REG_EN` (restored by `modeDidChange`), engine setup registers (rewritten by `engineEnable`), overlay registers (the overlay is disabled on will; re-enable is a client action), the hardware cursor block in VRAM (the framebuffer's), DMA descriptor tables in system RAM (survive; physical addresses unchanged). The decisive check is the wake verify itself: BUS_CNTL bit 27, CRTC_GEN_CNTL bit 25, `GUI_STAT` idle, `MEM_CNTL` bits 25:24 (see byte-order-reconcile.md section 5; the endian fields are set by the framebuffer on a mode change, and a sleep with a changed connection signature runs one).
6. **Display sleep versus system sleep.** State 0 of the NDRV may be used for display sleep too (not established); then the (3,1)/(4,1) pair is not "system" sleep and can occur while the machine runs and clients are active. Design for that: the gate must make clients wait or fail fast, never block the kernel thread indefinitely.
7. **Sleep trigger context.** `fbEvent` runs on the notifier thread holding IOFramebuffer's gate (`closeGate` in `checkPowerWork`): our handler must be bounded (drain with the existing timeout, no `IOSleep` loops) or it delays system sleep.

## 6. Proposed implementation (do not start without agreement)

Hook point: **keep the IOFramebuffer notification route** (as stock does). Do **not** add an IOService PM registration (`PMinit`/`joinPMtree`/`setPowerState`): our kext and the framebuffer are siblings under the PCI nub, the PM tree gives no ordering guarantee between siblings, so our `setPowerState(0)` could run after the NDRV had already suspended the chip and our drain would then read a dead chip; the framebuffer's own notification is delivered *before* its chip suspend by construction (section 5 item 1). A PM registration remains a possible *addition* only for machines whose framebuffer is not an `IOFramebuffer` (not the Lombard; not the G4 stub).

New file `kext/RageLTPower.cpp` (the design already names `RageLTPower`, flag `RAGE_FEAT_SLEEPWAKE`), small:
1. **State:** `fPower` in {Awake, Quiet, Asleep}; `fSleepFlag` (info != 0 pair, idempotent like stock `this[0x7f]`); `fModeDepth` stays for the info-0/1/2 pair.
2. **`fbEvent` table** (mirror of stock, section 2.3): add `(3, info != 0)` -> `systemWillSleep()`, `(4, info != 0)` -> `systemDidWake()`; log (do not act on) events 5-8; log 9/10.
3. **`systemWillSleep()`:** under `fLock`: if not already quiet, run the existing `modeWillChange()` body (drain with the existing bounded wait, disable overlay, invalidate contexts, unreserve), set `fPower = Asleep` (gate closed), record `MEM_CNTL`, `BUS_CNTL`, `CRTC_GEN_CNTL`, PCI command and BAR0 into the event log (`RAGE_EV_MARK`, a read-only before-image; these reads happen *before* the chip suspends because the event arrives first). No user-mapping redirect is needed: our clients never map chip memory or VRAM (grep: the only `map` is the kernel's `fFB->map`); stock needs the redirect only because its clients map registers.
4. **`systemDidWake()`:** (a) PCI first, no chip access: read command and BAR0; if memory decode or bus master is off, re-enable (`setMemoryEnable`, `setBusMasterEnable`) and log; if BAR0 reads 0 or the vendor/device id is wrong, **stay Asleep** (gate closed, log, return) rather than touching the chip. (b) Then `modeDidChange()`'s body: `BUS_EXT_REG_EN`, `engineEnable()` (already verifies BUS_CNTL bit 27 and CRTC_GEN_CNTL bit 25 and fails safe), `reserveDisplay()`, plus one new check of MEM_CNTL bits 25:24. (c) Compare the after-image with the before-image and log every difference (this is also the experiment: it tells the Lombard tester what the NDRV changed). (d) Open the gate, bump the generation (even) so the bundle rebuilds.
5. **Gate:** one inline `bool chipOK()` (`!(fModeGen & 1) && fPower == Awake`) at the top (under `fLock`) of every ungated function in section 3, returning `kIOReturnNotReady`; no new locks. The GL client's first-open path must use it too (the first chip read of a session).
6. **Idempotence and recovery:** a did without a will is logged and still verified; a will while already quiet only increments; a watchdog is *not* added (a stuck pair is a bug to find, not hide), but `RAGE_EV` marks make it visible.
7. **Out of scope (stock does not do it either, and the NDRV owns it):** saving/restoring CRTC/DAC/PLL/FIFO/cursor/LCD/backlight; GP_IO sequencing; lid/clamshell; head routing.

Test hooks needed: the stub's emitter (section 7, B1) and a `RAGE_GL_CONFIG`-style debug selector (`sleep-sim will|did [info]`) that invokes the same functions as the notifier, so the host-side/ENGTEST tests do not depend on IOGraphics.

## 7. Test plan, by risk tier

**Tier A: host / kext self-test, no hardware risk beyond what ENGTEST already does**
- A1. Host test of the event state machine (like `hosttest/modeset_test`): feed the sequences (1,0)(2,0); (3,0)(4,0); (3,1)(4,1); (3,0)(3,1)(4,1)(4,0); (3,1)(3,0)(4,0)(4,1); did-without-will; will-without-did; nested; assert gate open/closed after each, generation parity, counters, idempotence.
- A2. ENGTEST extension (the existing 9/9 mode-change simulation): add `sleep-sim` rounds and assert every ungated function returns NotReady while asleep (a negative test per function in the section 3 list; reads nothing from the chip because the gate returns first).
- A3. Wake-verify unit test with fake config/BAR values (BAR0 = 0, command = 0, vendor id wrong -> stays asleep; command repaired -> proceeds).

**Tier B: G4 live, low risk (chip is never suspended; all notifications are software)**
- B1. Extend `RageStubFB` to behave like the NDRV *toward IOGraphics*: register a 3-state PM (`initForPM`-style: `PMinit`, `joinPMtree`, `registerPowerDriver`) and implement `setAttribute('powr', state)` calling `handleEvent(7,0)`/`(6,0)`/`(5,0)`/`(8,0)` exactly like `ndrvSetPowerState`, plus `deliverFramebufferNotification(3, 1)` / `(4, 1)` at state 0 entry/exit, with **no chip writes** (the stub's power handler only emits events and logs). This also moves the rig closer to the Lombard (user goal: better test parity) and lets IOGraphics' own `checkPowerWork`/'vrsv' path run against our kext. (The stub answering `'vrsv'` = decline, so IOGraphics will not save the screen: nothing to restore.)
- B2. With a GL client running (Atlantis windowed + a fullscreen overlay client), force the sequences through `sleep-sim` first, then through real display power changes (`pmset -a dim 1 sleep 0` with display sleep after N minutes: **display sleep only**, system sleep disabled; the CRT may stay on because the stub does no DPMS, which is fine). Pass criteria: no chip access while asleep (event log), generation parity, textures re-uploaded, targets rebuilt, `gl_suite` 290/290 afterwards, IOMalloc/ownership counters unchanged, overlay disabled and re-enable possible.
- B3. Negative control: in tier B the chip is live during the simulated asleep window, so calling `vramCopyOut` then is safe. Show that it returns NotReady with the gate in place and succeeds with the gate compiled out for that one function, which proves the gate (not luck) is what stops the call.

**Tier C: G4, real system sleep (needs the user present to wake the machine; may need recovery)**
Hazard (not established either way): the MDD may cut power to PCI slots in sleep. A never-POSTed/power-cycled Rage hangs the first register read (ledger L11). So the protocol is staged and never reads the chip first:
- C0. Before any sleep: save a chip-state dump with the existing read-only tools (`chipinfo`/`regDump`: BUS_CNTL, MEM_CNTL, EXT_MEM_CNTL, CRTC_GEN_CNTL, CRTC_OFF_PITCH, DAC_CNTL, GEN_TEST_CNTL, HW_DEBUG, CRTC_INT_CNTL, CLOCK/PLL if read access exists), PCI config of the card (command, BAR0..2), and three VRAM canary words in the top reserved block (0x770000.., never engine-written) plus one in client-owned VRAM. Log marks; mirror to UDP; `F_FULLFSYNC` (G4 crash-evidence rules).
- C1. Install a **wake-time PCI-config-only probe** that runs before any chip read and decides whether the machine may proceed (tier-B stub extended with a `systemWake`-style hook, or a tiny kext). If vendor/device/BAR0 are intact: go on. If not: do nothing and let the user reboot.
- C2. Sleep with `osascript -e 'tell application "Finder" to sleep'` run in the user's GUI session (`pmset` has no `sleepnow`), user wakes the machine with a key; the after-dump is compared with C0. This answers, for the MDD slot only: are chip registers retained, is VRAM retained, is PCI config restored (`IOPCIDevice::restoreDeviceState`), does anything hang.
- C3. Only if C2 shows the card kept its state: repeat with the kext's `systemWillSleep/systemDidWake` live (needs B1's stub so the events exist) and a GL client open; criteria as B2. If the card lost its state: the stub needs a **blind replay** of its init table on wake (the table exists, 1872 writes, no reads gate it, `RageStubFB::replayInit`) before any read; that is a stub feature, not a product one, and it is only worth building if the user wants the rig to survive sleep.
- Each Tier C run is user-attended. A hang means a power cycle by the user.
