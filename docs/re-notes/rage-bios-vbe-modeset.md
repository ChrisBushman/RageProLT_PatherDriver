# Setting a display mode through the Rage option ROM (Nov 20 2026)

Finding: after the boot-time init (`biosrun -H -S`) every VBE 4F02 mode set fails (`ax=014f`) and the CRTC stays off.
Cause (traced in the x86 simulator, `tools/biosemu/biosrun` options `-X`, `-V`, env `BIOS_POKE`, `BIOS_PREMODE`, `BIOS_PRECX`, `BIOS_ITRACE`):
* the ROM's mode feasibility check (0x49c8 -> 0x59ea -> 0x9d6a) reads the byte at reg 0x8a (SCRATCH_REG2 bits 18:16, the active-display class) and jumps through a table; 0 = fail;
* that byte is written by the active-display sync code at the end of INT10 `AX=A083h` (ATI extension), but only when scratch byte 0x8f bit 6 (SCRATCH_REG3 bit 30) is set; init clears it, the PC system BIOS normally sets it;
* with reg 0x8c = 0x40000000 and `A083h` CX=0 the sim returns `4F02` success. Final sim registers for mode 0112 are textbook 640x480@60: H total 0x63 disp 0x4f sync 0x51/width 0x0c, V total 0x20c disp 0x1df sync 0x1e9/width 2, OFF_PITCH 0x14000000 (pitch 640, offset 0), CRTC_GEN_CNTL 0x4b0b0540 (EXT_DISP_EN, CRTC_EN), LCD_GEN_CTRL 0x49 (CRT_ON, LCD off).
* `A083h` CH bit1 drives the TV-out block (regs 0x74/0x9c = TV_OUT_INDEX/DATA), CH bit0 is the LCD path (waits on CRTC_VLINE); CX=0 avoids both.
Note: biosrun's HW backend forwards only the mach64 register window; VGA port (0x3xx) accesses stay simulated, fine for native-mode (EXT_DISP_EN) scanout.

## Result on the MDD Rage (Nov 20 2026): first light
Sequence (post-boot, manual): kextload Mach64Accelerator; `BIOS_POKE=8c:40000000 BIOS_PREMODE=a083 BIOS_PRECX=0000 biosrun -H -S -V 0112 rage.rom`; `mach64_fbpattern bars`; `mach64_blank off`.
* Hardware CRTC registers matched the simulator (640x480, 24 bpp packed, pitch 1920, offset 0). Monitor had sync but a black screen.
* Cause of black: `CRTC_GEN_CNTL` bit 6 `CRTC_DISPLAY_DIS` (blanking forced) is left set; the ROM normally clears the VGA sequencer screen-off bit instead, but biosrun does not forward VGA ports (0x3xx) to the chip. The palette was already a linear ramp.
* After `mach64_blank off` (bit 6 cleared) the monitor shows the colour bars and grey ramp: the Rage scans out VRAM offset 0.

## Stage A: Apple's present path onto the live display (Nov 20 2026, MDD)
* ROM offers only 8/15/16/24 bpp (no 32). Used VBE 0110h (640x480, 15 bpp 5-5-5, pitch 1280, offset 0, CRTC_PIX_WIDTH 3); `RageStubFB` now reports `IO16BitDirectPixels`, 1280 bytes/row (old binary: /Library/RageProLT/RageStubFB.stub32.bak on the MDD).
* `boot/bringup.sh` (loads patched ATIRagePro + stub) does not disturb the CRTC state; `stubctl notify` runs as before (offset-0 guard prints "not reserved, heap in use" because the first block is at 0x96000: the scanout buffer at offset 0 is not in Apple's heap, so there is no offset-0 hazard with a live framebuffer to investigate separately).
* The Apple backing surface is 32 bpp (pitch 2560, VRAM offset 0x97000 for 640x480) even though the display is 15 bpp; `surface_flush` converts it into the 15 bpp scanout: bytes read back 0x7c00/0x03e0/0x001f/0x7fff for R/G/B/white and the user confirmed the four bands + border over the whole screen.
* `tools/mach64_present.c` is the headless variant of `mach64_fspresent` (the old test dereferenced the VRAM offset returned by write_lock as a pointer and segfaulted). VRAM is little-endian: paint with OSWriteLittleInt32.

## Stage B2: WindowServer adopts the stub framebuffer (Nov 20 2026, MDD)
* The stub now has one CRT connection (`getConnectionCount` 1; attributes: flags 0, enable 1, sync 0; timing = kIOTimingIDVESA_640x480_60hz; CLUT/gamma calls accepted as no-ops) and logs every IOFramebuffer call. IOGraphics then creates `display0` (+ `AppleDisplay`) and WindowServer opens it: observed calls = getAttribute('crsr') unsupported (software cursor), getAttributeForConnection lddc/enab/pcnt/flgs/hddc/asns/thrm, getCurrentDisplayMode, getTimingInfo, setAttributeForConnection flgs, setGammaTable x3.
* **WindowServer only enumerates framebuffers at its own start.** SystemStarter runs in parallel with loginwindow, so WindowServer (boot +~6 s) starts before any startup item can load the stub. A logout does not restart it. Killing it (explicitly authorised by the user) makes init restart it and it then adopts the stub. `RageProInit` therefore has an opt-in `load-stack` file that runs bringup.sh at boot (stub exists early) but a WindowServer restart is still needed.
* Result with the 15 bpp 5-5-5 stub: the desktop background appears on the Rage monitor with **wrong colours**: the G4 is big-endian and WindowServer stores 16-bit pixels MSB first while the chip reads little-endian.
* Byte order experiment (kept behind `-DRAGE_UPPER_APERTURE_SWAP`, OFF): `MEM_CNTL` bits 27:26 = UPPER_APER_ENDIAN (01 = big-endian 16 bpp swapping) and report the upper 8 MB of BAR0 as aperture AND VRAM range. WindowServer then needed both ranges in the same view (with VRAM range at the lower 8 MB it computed an 8 MB offset and crashed in CGSCopyDRAMToVRAM at 0xb0818000, crash-looping until init throttled the console). With both ranges in the swapped view the suite failed 12+ texture checks: **Apple's patched kernel texture upload (and anything else of Apple's kext that copies through the stub's ranges) uses the same mapping**, so it received 16-bit-swapped data. Reverted; suite 188/188 again.
* Options not yet tried: swap texel/pixel words in our `tex_handler` UPLOAD when the aperture is swapped; use a different pixel format whose byte order does not depend on the CPU (8 bpp CLUT, then colours come from the palette via setCLUTWithEntries); or give WindowServer a separate mapping (a second IOMemoryDescriptor) while Apple's kext keeps the lower view.

### Byte order, solved (Nov 20 2026, option 2): separate views for WindowServer and Apple's kext
* Logging in the stub showed who asks for what: Apple's ATIRagePro calls `getVRAMRange` exactly once, from its start(), in **kernel-task** context, and never `getApertureRange`; WindowServer calls `getApertureRange(0)` and `getVRAMRange` many times, all in **USER-task** context (IOFramebufferUserClient inside its IOConnectMapMemory).
* So the stub serves two views of the same VRAM: kernel callers get BAR0[0, 8 MB) (unswapped, exactly as before), user-task callers get BAR0[8 MB, 16 MB) with `MEM_CNTL.UPPER_APER_ENDIAN` = 01 (big-endian 16 bpp swapping, set by `checkDisplay`). WindowServer needs both its ranges in the same view. The swap is done by the chip's bus interface: no per-pixel CPU cost.
* Result: the suite passes 188/188 with the swap on, WindowServer starts without crashing, and the user confirmed the Rage desktop shows **correct colours**.
* Stale `-DRAGE_UPPER_APERTURE_SWAP` experiment code was replaced by this (`RageStubFB::viewRange`).
* Still needed after every boot: restart WindowServer once (it enumerates framebuffers only at its own start, which is before any startup item can load the stub).

## In-kernel init replay (Nov 21 2026): no userspace ROM run, no WindowServer race
* Why the race existed: OpenFirmware never POSTs this PC card, so `biosrun` ran the option ROM from userspace after boot, and the stub/kexts loaded after WindowServer had enumerated displays.
* The ROM's whole effect on the chip, for init + VBE mode 0110, is **1872 register writes** (770 are DAC palette entries), the PCI command write, and two accesses `biosrun` makes itself (`0x8c = 0x40000000`, `BUS_CNTL |= 1<<27`). Three hardware traces (`biosrun -H`, `BIOS_TSTAMP=1`, exact-offset trace) have **identical write sequences**; no read gates anything (no status-poll loops); the only waits are 15 timer delays of 10-200 ms (0.55 s total), which the table carries as `delay_us`.
* `tools/rageinit/gen_table.py` builds `kext/stubfb/rage_init_table.h` from those traces; `RageStubFB::replayInit()` replays it from `start()`. Guards: personality property `RageReplayInit`, boot-arg `rage_noinit` (safety valve), chip answers CHIP_ID 0x4c49, mode not already set (a ROM-initialised boot is never touched), once per boot. After the replay it clears the 640x480x2 scanout (video memory is not cleared by a warm reset and decays without refresh: boot-time bands/sparse wrong pixels until WindowServer repainted).
* **Equivalence proof**: `tools/mach64_regdump.c` dumps registers 0x00-0xfc and the 256-entry palette; ROM-initialised boot vs replay boot differ in **0 of 318 lines**.
* Install: `RageStubFB.kext` in `/System/Library/Extensions` with `OSBundleRequired=Console` (goes into `Extensions.mkext`: `kextcache -l -m /System/Library/Extensions.mkext /System/Library/Extensions`), `/Library/RageProLT/no-biosrun` so the startup item skips the ROM run, Apple's patched ATIRagePro + the accelerator still load from the startup item after boot (`bringup.sh` detects the already-loaded stub and sends `stubctl probe`). WindowServer then finds the Rage at its own start; no restart needed.

## Which modes the ROM accepts, and at what refresh (Nov 25 2026, simulator, offline)
Run: `BIOS_POKE=8c:40000000 BIOS_PREMODE=a083 BIOS_PRECX=0000 [BIOS_POKE2=80:05041570] biosrun -S -V <mode> rage.rom` (pure simulation, builds on Linux with `cc -std=gnu99 -w -Ilibx86emu -Ilibx86emu/include biosrun.c libx86emu/*.c`, no `-DHW`). New hooks: `BIOS_POKE2` (second poke after the pre-mode call), scratch-register print, `BIOS_EDID`/`BIOS_A013` (EDID call).
* **Rule (from the Programmer's Guide A.34 + verified):** a mode is refused (AX=014f) unless (a) the display class (SCRATCH_REG2 bits 18:16 after `A083h`) is 2, and (b) the refresh-mask byte for its resolution in SCRATCH_REG0 is non-zero: byte 0 = 640x480 (bit 6 72 Hz, 5 75 Hz, 4 85 Hz), byte 1 = 800x600 (bit 4 85, 3 56, 2 60, 1 72, 0 75 Hz), byte 2 = 1280x1024 (bit 5 85, 4 43i, 3 47, 2 60, 1 70, 0 75 Hz), byte 3 = 1024x768 (bit 4 85, 3 87i, 2 60, 1 70, 0 75 Hz). At boot the system BIOS/EEPROM fills these; the replay boot leaves them 0, so only 640x480/640x400 worked. The ROM picks the **highest enabled rate**.
* With masks 640=0x70, 800=0x15, 1280=0x04, 1024=0x05 every standard mode (0101 0103 0105 0107, 0110-0112, 0113-0115, 0116-0118, 0119-011b) is accepted. Resulting CRTC (H_TOTAL_DISP / V_TOTAL_DISP): 640x480 0x004f0067/0x01df01fc (832x509, 85 Hz), 800x600 0x00630082/0x02570276 (1048x631, 85 Hz, 56.25 MHz), 1024x768 0x007f00a3/0x02ff031f (1312x800, 75 Hz), 1280x1024 0x009f00d2/0x03ff042a (1688x1067, 60 Hz): all inside the Dell 828FI limits (30-70 kHz, 50-120 Hz, 110 MHz) except where noted in the mode table work.
* The sim trace holds the PLL (CLOCK_CNTL) programming, DSP_CONFIG/DSP_ON_OFF and the palette; the CRTC values reach the chip through the simulated VGA ports, so they are read from the final simulated register state, not from CHIP-WR lines.
