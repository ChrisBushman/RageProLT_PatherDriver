# Setting a display mode through the Rage option ROM (Nov 20 2026)

Finding: after the boot-time init (`biosrun -H -S`) every VBE 4F02 mode set fails (`ax=014f`) and the CRTC stays off.
Cause (traced in the x86 simulator, `tools/biosemu/biosrun` options `-X`, `-V`, env `BIOS_POKE`, `BIOS_PREMODE`, `BIOS_PRECX`, `BIOS_ITRACE`):
* the ROM's mode feasibility check (0x49c8 -> 0x59ea -> 0x9d6a) reads the byte at reg 0x8a (SCRATCH_REG2 bits 18:16, the active-display class) and jumps through a table; 0 = fail;
* that byte is written by the active-display sync code at the end of INT10 `AX=A083h` (ATI extension), but only when scratch byte 0x8f bit 6 (SCRATCH_REG3 bit 30) is set; init clears it, the PC system BIOS normally sets it;
* with reg 0x8c = 0x40000000 and `A083h` CX=0 the sim returns `4F02` success. Final sim registers for mode 0112 are textbook 640x480@60: H total 0x63 disp 0x4f sync 0x51/width 0x0c, V total 0x20c disp 0x1df sync 0x1e9/width 2, OFF_PITCH 0x14000000 (pitch 640, offset 0), CRTC_GEN_CNTL 0x4b0b0540 (EXT_DISP_EN, CRTC_EN), LCD_GEN_CTRL 0x49 (CRT_ON, LCD off).
* `A083h` CH bit1 drives the TV-out block (regs 0x74/0x9c = TV_OUT_INDEX/DATA), CH bit0 is the LCD path (waits on CRTC_VLINE); CX=0 avoids both.
Note: biosrun's HW backend forwards only the mach64 register window; VGA port (0x3xx) accesses stay simulated, fine for native-mode (EXT_DISP_EN) scanout.

## Result on the MDD Rage (Nov 20 2026): first light
Sequence (post-boot, manual): kextload Mach64Accelerator; `BIOS_POKE=8c:40000000 BIOS_PREMODE=a083 BIOS_PRECX=0000 biosrun -H -S -V 0112 rage.rom`; `mach64_fbpattern bars`; `mach64_blank off`.
* Hardware CRTC registers matched the simulator (640x480, 24 bpp packed, pitch 1920, offset 0). Monitor had sync but a black screen.
* Cause of black: `CRTC_GEN_CNTL` bit 6 `CRTC_DISPLAY_DIS` (blanking forced) is left set; the ROM normally clears the VGA sequencer screen-off bit instead, but biosrun does not forward VGA ports (0x3xx) to the chip. The palette was already a linear ramp.
* After `mach64_blank off` (bit 6 cleared) the monitor shows the colour bars and grey ramp: the Rage scans out VRAM offset 0.

## Stage A: Apple's present path onto the live display (Nov 20 2026, MDD)
* ROM offers only 8/15/16/24 bpp (no 32). Used VBE 0110h (640x480, 15 bpp 5-5-5, pitch 1280, offset 0, CRTC_PIX_WIDTH 3); `RageStubFB` now reports `IO16BitDirectPixels`, 1280 bytes/row (old binary: /Library/RageProLT/RageStubFB.stub32.bak on the MDD).
* `boot/bringup.sh` (loads patched ATIRagePro + stub) does not disturb the CRTC state; `stubctl notify` runs as before (offset-0 guard prints "not reserved, heap in use" because the first block is at 0x96000: the scanout buffer at offset 0 is not in Apple's heap, so there is no offset-0 hazard with a live framebuffer to investigate separately).
* The Apple backing surface is 32 bpp (pitch 2560, VRAM offset 0x97000 for 640x480) even though the display is 15 bpp; `surface_flush` converts it into the 15 bpp scanout: bytes read back 0x7c00/0x03e0/0x001f/0x7fff for R/G/B/white and the user confirmed the four bands + border over the whole screen.
* `tools/mach64_present.c` is the headless variant of `mach64_fspresent` (the old test dereferenced the VRAM offset returned by write_lock as a pointer and segfaulted). VRAM is little-endian: paint with OSWriteLittleInt32.

## Stage B2: WindowServer adopts the stub framebuffer (Nov 20 2026, MDD)
* The stub now has one CRT connection (`getConnectionCount` 1; attributes: flags 0, enable 1, sync 0; timing = kIOTimingIDVESA_640x480_60hz; CLUT/gamma calls accepted as no-ops) and logs every IOFramebuffer call. IOGraphics then creates `display0` (+ `AppleDisplay`) and WindowServer opens it: observed calls = getAttribute('crsr') unsupported (software cursor), getAttributeForConnection lddc/enab/pcnt/flgs/hddc/asns/thrm, getCurrentDisplayMode, getTimingInfo, setAttributeForConnection flgs, setGammaTable x3.
* **WindowServer only enumerates framebuffers at its own start.** SystemStarter runs in parallel with loginwindow, so WindowServer (boot +~6 s) starts before any startup item can load the stub. A logout does not restart it. Killing it (explicitly authorised by the user) makes init restart it and it then adopts the stub. `RageProInit` therefore has an opt-in `load-stack` file that runs bringup.sh at boot (stub exists early) but a WindowServer restart is still needed.
* Result with the 15 bpp 5-5-5 stub: the desktop background appears on the Rage monitor with **wrong colours**: the G4 is big-endian and WindowServer stores 16-bit pixels MSB first while the chip reads little-endian.
* Byte order experiment (kept behind `-DRAGE_UPPER_APERTURE_SWAP`, OFF): `MEM_CNTL` bits 27:26 = UPPER_APER_ENDIAN (01 = big-endian 16 bpp swapping) and report the upper 8 MB of BAR0 as aperture AND VRAM range. WindowServer then needed both ranges in the same view (with VRAM range at the lower 8 MB it computed an 8 MB offset and crashed in CGSCopyDRAMToVRAM at 0xb0818000, crash-looping until init throttled the console). With both ranges in the swapped view the suite failed 12+ texture checks: **Apple's patched kernel texture upload (and anything else of Apple's kext that copies through the stub's ranges) uses the same mapping**, so it received 16-bit-swapped data. Reverted; suite 188/188 again.
* Options not yet tried: swap texel/pixel words in our `tex_handler` UPLOAD when the aperture is swapped; use a different pixel format whose byte order does not depend on the CPU (8 bpp CLUT, then colours come from the palette via setCLUTWithEntries); or give WindowServer a separate mapping (a second IOMemoryDescriptor) while Apple's kext keeps the lower view.

### Byte order, solved (Nov 20 2026, option 2): separate views for WindowServer and Apple's kext
* Logging in the stub showed who asks for what: Apple's ATIRagePro calls `getVRAMRange` exactly once, from its start(), in **kernel-task** context, and never `getApertureRange`; WindowServer calls `getApertureRange(0)` and `getVRAMRange` many times, all in **USER-task** context (IOFramebufferUserClient inside its IOConnectMapMemory).
* So the stub serves two views of the same VRAM: kernel callers get BAR0[0, 8 MB) (unswapped, exactly as before), user-task callers get BAR0[8 MB, 16 MB) with `MEM_CNTL.UPPER_APER_ENDIAN` = 01 (big-endian 16 bpp swapping, set by `checkDisplay`). WindowServer needs both its ranges in the same view. The swap is done by the chip's bus interface: no per-pixel CPU cost.
* Result: the suite passes 188/188 with the swap on, WindowServer starts without crashing, and the user confirmed the Rage desktop shows **correct colours**.
* Stale `-DRAGE_UPPER_APERTURE_SWAP` experiment code was replaced by this (`RageStubFB::viewRange`).
* Still needed after every boot: restart WindowServer once (it enumerates framebuffers only at its own start, which is before any startup item can load the stub).

## In-kernel init replay (Nov 21 2026): no userspace ROM run, no WindowServer race
* Why the race existed: OpenFirmware never POSTs this PC card, so `biosrun` ran the option ROM from userspace after boot, and the stub/kexts loaded after WindowServer had enumerated displays.
* The ROM's whole effect on the chip, for init + VBE mode 0110, is **1872 register writes** (770 are DAC palette entries), the PCI command write, and two accesses `biosrun` makes itself (`0x8c = 0x40000000`, `BUS_CNTL |= 1<<27`). Three hardware traces (`biosrun -H`, `BIOS_TSTAMP=1`, exact-offset trace) have **identical write sequences**; no read gates anything (no status-poll loops); the only waits are 15 timer delays of 10-200 ms (0.55 s total), which the table carries as `delay_us`.
* `tools/rageinit/gen_table.py` builds `kext/stubfb/rage_init_table.h` from those traces; `RageStubFB::replayInit()` replays it from `start()`. Guards: personality property `RageReplayInit`, boot-arg `rage_noinit` (safety valve), chip answers CHIP_ID 0x4c49, mode not already set (a ROM-initialised boot is never touched), once per boot. After the replay it clears the 640x480x2 scanout (video memory is not cleared by a warm reset and decays without refresh: boot-time bands/sparse wrong pixels until WindowServer repainted).
* **Equivalence proof**: `tools/mach64_regdump.c` dumps registers 0x00-0xfc and the 256-entry palette; ROM-initialised boot vs replay boot differ in **0 of 318 lines**.
* Install: `RageStubFB.kext` in `/System/Library/Extensions` with `OSBundleRequired=Console` (goes into `Extensions.mkext`: `kextcache -l -m /System/Library/Extensions.mkext /System/Library/Extensions`), `/Library/RageProLT/no-biosrun` so the startup item skips the ROM run, Apple's patched ATIRagePro + the accelerator still load from the startup item after boot (`bringup.sh` detects the already-loaded stub and sends `stubctl probe`). WindowServer then finds the Rage at its own start; no restart needed.

## Which modes the ROM accepts, and at what refresh (Nov 25 2026, simulator, offline)
Run: `BIOS_POKE=8c:40000000 BIOS_PREMODE=a083 BIOS_PRECX=0000 [BIOS_POKE2=80:05041570] biosrun -S -V <mode> rage.rom` (pure simulation, builds on Linux with `cc -std=gnu99 -w -Ilibx86emu -Ilibx86emu/include biosrun.c libx86emu/*.c`, no `-DHW`). New hooks: `BIOS_POKE2` (second poke after the pre-mode call), scratch-register print, `BIOS_EDID`/`BIOS_A013` (EDID call).
* **Rule (from the Programmer's Guide A.34 + verified):** a mode is refused (AX=014f) unless (a) the display class (SCRATCH_REG2 bits 18:16 after `A083h`) is 2, and (b) the refresh-mask byte for its resolution in SCRATCH_REG0 is non-zero: byte 0 = 640x480 (bit 6 72 Hz, 5 75 Hz, 4 85 Hz), byte 1 = 800x600 (bit 4 85, 3 56, 2 60, 1 72, 0 75 Hz), byte 2 = 1280x1024 (bit 5 85, 4 43i, 3 47, 2 60, 1 70, 0 75 Hz), byte 3 = 1024x768 (bit 4 85, 3 87i, 2 60, 1 70, 0 75 Hz). At boot the system BIOS/EEPROM fills these; the replay boot leaves them 0, so only 640x480/640x400 worked. The ROM picks the **highest enabled rate**.
* With masks 640=0x70, 800=0x15, 1280=0x04, 1024=0x05 every standard mode (0101 0103 0105 0107, 0110-0112, 0113-0115, 0116-0118, 0119-011b) is accepted. Resulting CRTC (H_TOTAL_DISP / V_TOTAL_DISP): 640x480 0x004f0067/0x01df01fc (832x509, 85 Hz), 800x600 0x00630082/0x02570276 (1048x631, 85 Hz, 56.25 MHz), 1024x768 0x007f00a3/0x02ff031f (1312x800, 75 Hz), 1280x1024 0x009f00d2/0x03ff042a (1688x1067, 60 Hz): all inside the Dell 828FI limits (30-70 kHz, 50-120 Hz, 110 MHz) except where noted in the mode table work.
* The sim trace holds the PLL (CLOCK_CNTL) programming, DSP_CONFIG/DSP_ON_OFF and the palette; the CRTC values reach the chip through the simulated VGA ports, so they are read from the final simulated register state, not from CHIP-WR lines.

## Mode table (option 2, agreed Nov 25): `tools/rageinit/gen_modes.py` -> `rig/stubfb/rage_modes.h`
* 12 rows (640x480, 800x600, 1024x768, 1280x1024 at 15/16/24 bpp) of the ROM's own final CRTC/DSP/pitch register values, generated from the simulator and gated against the Dell 828FI limits. Resulting timings equal the monitor manual's preset table (43.27, 53.67, 60.02 kHz; 85/85/75 Hz) and, for 1280x1024, 63.98 kHz / 59.96 Hz.
* Decoding rules (confirmed against VESA): H_TOTAL field = chars-1, H_DISP field = chars-1, H_SYNC start field = start/8 with a per-depth pipeline delay in bits 10:8, H_SYNC width = chars, V fields = lines-1 (sync start field = start-1), polarity in bit 21.
* **Not yet known / not in the table:** (1) the dot-clock PLL values: the simulator does not model the PLL, so its CLOCK_CNTL data bytes are stale read-backs and must not be used. Use the formula `pclk = 2 * 29.498928 MHz * fb_div / (ref_div * post)` (checked on the hardware replay: ref_div 0x40, fb_div 0xda, post-divider code 3 = x8 gives 25.12 MHz for the 640x480@60 clock); post-divider codes {1,2,4,8,3,-,6,12}; X.Org recipe: reset VCLK (PLL_VCLK_CNTL reset bit), set the 2-bit post-divider field at clock*2 in PLL_VCLK_POST_DIV, extended divider bit in PLL_XCLK_CNTL, VCLKn_FB_DIV, release reset. (2) DSP_CONFIG/DSP_ON_OFF in the table are the simulator's, computed by the ROM from clocks it read back from the (unmodelled) PLL: treat as unverified until checked against the 640x480 hardware value and the X.Org `atidsp.c` formula. (3) UPPER_APER_ENDIAN per depth (16 bpp = 01, 32 bpp = 10).
* Verification plan: writer reproduces `0110` and its register dump equals the ROM-booted chip's (mach64_regdump, 0 of 318 lines) before any other mode is tried; measure the real frame rate from the vertical-blank interval to verify the PLL.

## Mode-set plan (`rig/stubfb/rage_modeset.h`) and its host proof (Nov 25)
`hosttest/modeset_test.c` seeds a register model with the ROM-booted hardware state (decoded from `rage_init_table.h`), scrambles the fields the plan sets, runs the plan for 640x480 15 bpp 25.175 MHz and diffs against the hardware: **every CRTC/pitch/GEN_CNTL/DSP_CONFIG register and PLL 4..0xb match; the only difference is DSP_ON_OFF** (plan 0x00c007ae vs ROM 0x009c07b0; DSP_OFF 1966 vs 1968 and DSP_ON 192 vs 156). Also, the ROM leaves the display blanked (GEN_CNTL bit 6) and the stub un-blanks it, so that bit is excluded. Tried memory type 0-5, VRAM 2/4/8 MB and FIFO depth 24/32: none yields 156, so the ROM's DSP_ON assumption is **not established**. Plan order: blank, VCLK reset, post-div, XDIV, FB_DIV (VCLK3 = PLL reg 0xa), release, 10 ms lock wait, DSP, CRTC, pitch, GEN_CNTL depth, un-blank. 15 bpp rows only so far: the 16/24 bpp rows' CRTC values are the simulator's and unproven on hardware.

## 32 bpp scanout (Nov 25, verified live)

* The ROM has no 32 bpp mode. Rows are the ROM's 24 bpp CRTC values with CRTC_PIX_WIDTH = 6 (`gen_modes.py`); DSP_CONFIG/DSP_ON_OFF come from the formula; MEM_CNTL UPPER_APER_ENDIAN = 2 (32 bpp) / 1 (16 bpp), switched with the depth.
* Offered at 640x480, 800x600, 1024x768 (60 Hz). 1280x1024 stays 15 bpp (VRAM budget).
* Supervised live results on the Dell 828FI via WindowServer (depth index 1, 25 s hold): all three modes stable, correct colours, correct picture position (user: "good colors, good image, position looks correct", "800x600 looks good", "looks good"). Accelerator at 32 bpp not yet exercised (step 2).
* Not verified: DSP_ON_OFF vs ROM (still unexplained), long-duration FIFO underrun behaviour under load.

### 32 bpp render targets (step 2, Nov 25)

* Kernel: ARGB8888 fills (colour = 0xAARRGGBB), Z clear unchanged (16 bit Z), same-format 32->32 present; present of a target whose depth differs from the scanout returns Unsupported (textured-quad present, step 3). `tools/ragegl/depth32_test.c`: 18/18 on the G4 at 800x600 32 bpp (fill, scissor, Z clear, 3D triangle 27355 px, present read back 6000/6000, 16->32 refused).
* Bundle: `mach64_build_surface` picks target bpp = scanout bpp (falls back to 16 if the 32 bpp allocation fails); pixel ops (read/draw/copy/bitmap/accum), CPU blend/stencil path, copy-to-texture, colour mask (bytes R,G,B,A from the top; 32 bpp mask is ARGB bits), clear colour, drawable descriptor pitch all handle 2 or 4 byte pixels. Z readback stays 16 bit.
* `gl_suite` is depth-aware (px / clear_rt). Results: 15 bpp 290/290; 800x600 32 bpp 290/290 (after fixing my own colour-mask byte order: 3 failures first run); `gl_probe` 128 pass / 1 fail (ARB fragment program) at both depths.
* Alpha: the target's destination alpha is reported as 1.0 by read/copy pixels; the engine's alpha writes into the 32 bpp target are not characterised yet.
* Not done: 1024x768 at 32 bpp needs a 16 bpp target (budget) -> not presentable until step 3.

### Textured-quad present (step 3, Nov 25)

* Kernel `RageLTDevice::presentEx` (RageLTMode.cpp) + `eng_texquad` (RageLTEngine.h): the target is read as a SQUARE power-of-two texture (pitch = 2^wl, height <= pitch, wl 3..10; the bundle allocates `pot_pitch` targets when the scanout is 32 bpp and the target 16 bpp) and drawn as two triangles into the scanout; the engine converts formats. `present()` routes there when the target/scanout pixel size differs; `RAGE_GL_PRESENT_SCALED` (selector 18) does an arbitrary source -> destination rectangle, nearest or bilinear. Register order = the bundle's proven textured path (m64_emit_state + triangles); S/T/W/ONE_OVER_AREA are built with integer arithmetic (`common/rage_f32.h`, bit-exact against the FPU over 14.3 M values, `hosttest/f32_test.c`) because the kext may not use the FPU (checkfp clean).
* Hardware (G4, 800x600 32 bpp scanout, `tools/ragegl/quad_test`): a 27-point sweep of sampling biases (RAGE_GL_CONFIG keys 3/4/5, defaults 0) shows the DEFAULT mapping is exact: 16 -> 32 conversion 3072/3072 pixels = 5/6-bit replication (r<<3 | r>>2); 2x nearest upscale 3072/3072; 2x bilinear vs a software 2x2 reference: mean error 4.35, max 25 (coarse chip weights, as measured Nov 24: 3.8); right-edge clip, off-screen no-op and out-of-target source refusal behave. `depth32_test` 19/19.
* Gates after the change at 15 bpp: gl_suite 290/290, ragegl_test 26/26, gl_probe 128/1.
* Open: speed (expected ~24 ms for a full 1024x768 quad) and an end-to-end 1024x768 32 bpp GL run; the bundle does not yet use the scaled selector (FS_SCALE policy: render at a reduced size and stretch) - the kernel op and `rgb_present_scaled` exist and are tested.

#### Textured-quad present: speed, and a texture-cache finding (Nov 25, G4)

* Full-screen 1024x768 into a 32 bpp scanout: **13.0 ms** 1:1 16->32 conversion (60 Mpix/s); **11.5 ms** nearest 2x upscale; **14.0 ms** bilinear 2x upscale (`quad_test bench` / `probe`). Through the bundle (`tools/ragegl/fs_test`, 1024x768 32 bpp scanout, 16 bpp power-of-two-pitch target): 9/9 pass, scanout readback matches, **13.4 ms** per full-screen present. Better than the 24 ms estimated from the Nov 24 measurement.
* **Finding (cost me an hour): TEX_CNTL bit 30 slows bilinear by ~40x on a pitch-1024 texture.** The bundle sets TEX_CNTL bit 30 (the DRI header calls it TEX_CACHE_SIZE_4K/2K, both = 1<<30). With it set, a bilinear read of a 128x96 region magnified to 256x192 from a texture of row pitch 1024 (2 KB rows) takes 47 ms, vs 1.0 ms for pitch 256 or 512 and 1.1 ms with bit 30 CLEARED. SCALE_3D_CNTL bit 9 (TEX_CACHE_SPLIT) set brings the slowness back. Nearest filtering is unaffected. Symptom looked like an engine hang (the next op's wait timed out after ~0.3 s and the kernel reset the engine): it was just a very slow draw. The quad now clears bit 30. **Open (not acted on):** the bundle's ordinary textured draws set bit 30 too, so large (pitch >= 1024 texel) bilinear textures in game rendering may suffer the same cliff; worth a separate measurement.
* Experiment knobs (RAGE_GL_CONFIG keys 3-8: texel/vertex bias, blend field, TEX_CNTL / SCALE_3D bit flips) default to 0 and stay in for later tuning.

#### Destination alpha, FS_SCALE policy, texture-cache cliff in the bundle (Nov 25, G4)

* **Destination alpha (measured, `tools/ragegl/alpha_test` 7/7 and `alpha16_test`; static basis: register reference ALPHA_TST_CNTL field `ALPHA_DST_SEL`, bits 10:8).** The ARGB8888 target stores alpha: 2D fill writes the colour's alpha exactly; a 3D triangle writes ALPHA_DST_SEL's choice (0 -> 00, 1 -> ff, 4 -> source alpha As, 5 -> 1-As (7f for 80), 6 -> Ad kept, 7 -> 1-Ad); the bundle's default (4 = As) therefore stores the vertex/texel alpha. DP_WRITE_MASK without the alpha bits leaves the alpha byte alone; an alpha-only mask changes only it. Blend factors DST_ALPHA / 1-DST_ALPHA read the stored Ad (also right after a 2D fill). A textured quad stores the texel's alpha (ARGB8888 texel 0x40 -> 0x40). 15 bpp (ARGB1555) targets store alpha in bit 15 (same ALPHA_DST_SEL write, DST_ALPHA blend reads it); `ragegl_fill` converts a 565 colour to 1555 so a fill cannot set that bit (draw with blend off to set it). Bundle consequence: `glReadPixels` on a 32 bpp target now returns the stored alpha (was a constant 1.0; `gld_pixels.c`; `gl_suite` t_dstalpha checks it at 32 bpp); 15/16 bpp targets still report 1.0 because their alpha bit is not written by clears.
* **FS_SCALE policy in the bundle** (`mach64_priv.fs_scale`): in full screen (win_mode 0), a drawable smaller than the scanout is presented stretched over the whole scanout, bilinear, through the kernel's scaled present (target gets a power-of-two pitch); windowed contexts and equal-size contexts keep the raw blit / 1:1 quad. In real full-screen use the bundle's drawable is the display size, so this only triggers for a deliberately smaller context (`g_gld_force_*` in tests, a future shrink-to-fit). `tools/ragegl/fs_test` phase 2 covers it.
* **Texture-cache cliff through the bundle (measurement only, `gl_suite cliff`; no texture state changed):** 15 bpp, bilinear-magnified 256x192 quad: 5.9 ms from a 256-wide RGB texture, 38.7 ms from a 1024-wide one (6.6x). The bundle sets TEX_CNTL bit 30 on every textured draw, the condition that made the quad's own pitch-1024 reads ~40x slower. Not yet tried: clearing bit 30 for textures of pitch >= 1024. Needs the user's decision (touches every game's texturing).
* **32 bpp scaled-present source is ~30x slower (Nov 25 hardware run, 1024x768 32 bpp scanout).** A 640x480 32 bpp target (pitch 1024 px = 4 KB rows) stretched by the quad took 387 ms per present and lost frames to the engine timeout; the same size as a 16 bpp target (2 KB rows) takes 13.8 ms. So FS_SCALE targets are 16 bpp (`gld_core.c`). Same family as the TEX_CNTL bit-30 / row-pitch cliff (cause not isolated). Result: fs_test 16/16, gl_suite 291/291, gl_probe 128/1 at 1024x768 32 bpp. (First suite run had one failure that was a wrong test expectation: px() forces alpha ff, glReadPixels correctly returned 0x80.)
* **TEX_CNTL bit 30 cleared in the bundle by default (Nov 25 measurement, G4, `gl_suite cliff`).** bit 30 set (old) vs clear, 256x192 quad, RGB texture: bilinear from a 256-wide texture 5.88 / 5.89 ms; bilinear from a 1024-wide texture 38.7 / 5.9 ms; 1024-wide 4x minified 27.8 / 5.8 ms; nearest (either width) and 256-wide minified 5.7 / 5.7 ms. Equal everywhere except the wide-bilinear cases, which are 4.8-6.6x faster. Full suite 291/291 at 15 and 32 bpp with it clear. Variant "clear only when >= 1024 wide" measured the same as always-clear, so the simpler form is used.
