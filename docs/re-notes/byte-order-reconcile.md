# Byte order (checklist A2 / ledger L9 / open item O4): reconciliation (Nov 26)

Question (remaining-work.md, A2): the ledger row L9 says "texels byte-reversed on the G4 stub rig; Lombard behaviour unknown" and design 3.6 / O4 call it open, while design 11.3 says it was resolved from documents. Which is right, what exactly was observed, is the observation consistent with 11.3, what is unproven, is any work left?

Method: grep of docs/ and `git log`; the pre-deletion code (`git show 55677a5^:...`, the Path-B plugin and patched kext); register diagrams rendered from the RRG (MEM_CNTL, PDF pages 80-81); static analysis of the stock `ATIRagePro.kext` (md5 8fc97891), `ATIRageProGA`, the Panther `IONDRVSupport`/`IOGraphicsFamily` kexts (read-only pull from the G4) and the NDRV decompile (`scratchpad/ndrv/out/funcs.c`). Nothing was run on the G4. Evidence levels: "static" = read from code or document; "derived" = computed from a stated model (a script, reproduced below); "not established" = no evidence.

## 1. Verdict in one paragraph

Design 11.3 is right for the **new** driver and ledger L9 / design 3.6 / O4 are stale: the new kernel never uses the framebuffer's VRAM view. It maps PCI BAR0 itself (`kext/RageLTDevice.cpp:29-30`, `getDeviceMemoryWithRegister(kIOPCIConfigBaseAddress0)->map`), writes through the lower 8 MB, and defines the byte image with explicit `RAGE_XFER_SWAP16/32` flags (`kext/RageLTMode.cpp:209-229`); this path is validated on the G4 (290/290 suite with coloured texture checks, `xfer_test` contract test). The old observation ("byte-reversed") was real but belonged to a different code path (Apple's kext, patched upload selector, plain `stw` through whatever VRAM view the framebuffer handed Apple's kext). Its two descriptions in the repo differ (full byte reversal on Nov 20, 16-bit halves exchange on Nov 21); the second is the better-evidenced one, and it has a precise signature: it is what a **16-bit byte-swapping aperture** does to a big-endian store, not what the plain unswapped view does. That signature is **not consistent with the stub's own comment** that Apple's kext received the unswapped lower view (section 4), so one of those two statements is wrong; it cannot be resolved statically and it no longer matters for the product. One real residual risk was found that 11.3 does not mention: **`LOWER_APER_ENDIAN`** (MEM_CNTL bits 25:24), which the Apple NDRV sets for its *second-CRTC* instance (section 5). It decides whether "the lower view is unswapped" holds on a Lombard with a second head. A cheap runtime guard closes it (section 7). No G4 live test is needed for O4.

## 3. What a store through each view does (derived, reproducible)

Model (RRG MEM_CNTL: LOWER/UPPER_APER_ENDIAN 00 = none, 01 = "big endian 16 bpp swapping", 10 = "32 bpp swapping"): a big-endian CPU stores the 32-bit value W = 0xAARRGGBB; memory bytes in ascending address order are `AA RR GG BB`; the aperture swap acts on the bus: 16-bit swapping exchanges the two bytes inside each aligned halfword, 32-bit swapping reverses all four. The chip then reads little-endian. The hardware ARGB8888 texel is the little-endian word 0xAARRGGBB (bytes `BB GG RR AA`): this is proven for the lower view by the current driver (SWAP32 writes exactly those bytes and the colour checks pass). Result (script run during this analysis, channel letters are which source byte ends up in the A,R,G,B position of the sampled word):

| CPU stores | via unswapped view | via 16-bit swap view (`01`) | via 32-bit swap view (`10`) |
|---|---|---|---|
| plain W (`stw`) | B G R A (full byte reversal) | **G B A R** | **A R G B (correct)** |
| W with 16-bit halves exchanged | R A B G | **A R G B (correct)** | G B A R |
| W byte-reversed (`stwbrx`) | **A R G B (correct)** | R A B G | B G R A |

Consequences:
1. The Nov 20 description ("0xffff0000 read back as 0x0000ffff") matches rows 1 *and* 2 of the first two columns (a symmetric value), which is why it was a misleading probe. The Nov 21 colour test is the discriminating one.
2. The Nov 21 observation is **G B A R from a plain store** and **correct after exchanging the halves**: that is exactly the "16-bit swap view" column, and it is *not* the unswapped column (which would show B G R A and would be fixed by a byte reversal). So the patched Apple kext's CPU pointer, on the stub rig, behaved as a **16-bit swapping view** (stub at 15 bpp: `UPPER_APER_ENDIAN` = 01).
3. The Nov 24 observation (new unswapped kernel path fed by the older plugin that pre-exchanges halves) predicts **R A B G**: the right word with the bytes swapped inside each 16-bit unit. Design 11.5 describes it as "16-bit halves swapped", which is a loose description of that pattern; no pixel dump was recorded, so this is consistent but not confirmed.
4. "Why was no swap needed with Apple's own framebuffer (Lombard)?": the plain-store/32-bit-swap-view cell is **correct without any CPU swap**. Static support (not proof): stock `ATIRagePro` takes its CPU pointer from the framebuffer's `getVRAMRange()->map()` (per-framebuffer record at `this+0xd0`, stride 0x1c: `0x42b8` calls IOFramebuffer vslot 0x5d0, `0x42d8` maps it with options 0x101, `0x42fc` stores the address at record+0x10 = `accel[0xe0]`), and `IONDRVFramebuffer::getVRAMRange` (0x2ed8) returns a descriptor (`this+0x16c`) built by `makeSubRange` (0x4684) around the base address the NDRV reports, which the NDRV places in the **upper, swapped** 8 MB (NDRV doc section 1; `0x800000 + offset`, code 0x1000d840). So on a Lombard at 32 bpp (UPPER = 10) Apple's plain `stw` lands correctly; at a 16-bit desktop (UPPER = 01) the same store would give G B A R. This predicts that stock-style CPU texture stores on a real Lombard are depth dependent. **Inferred**, depends on `makeSubRange`'s base being the NDRV's upper-aperture base; not decoded to the last step.

## 4. Is the observation consistent with 11.3?

- With the **architecture** of 11.3 (swap alias exists, framebuffer owns it, lower view unswapped, kernel byte image explicit): yes. The observation is a textbook case of the alias swapping at 16-bit granularity when the CPU wrote through it.
- With the **stub-rig explanation** in `memory-map.md` 5c and the comment in `RageStubFB::viewRange` (Apple's kext was handed the *plain lower* view): **no, they conflict.** By section 3, a plain store through the unswapped view gives B G R A, not G B A R, and the halves-exchange fix could not have made the suite pass. Either (a) at the time of the colour test Apple's kext's pointer was in fact a swapped view (for example the kext's map was created in a context the `current_task() == kernel_task` test did not classify as expected, or the stub build used for the test returned the upper view to kernel callers), or (b) the colour-test description is wrong. The code path no longer exists (deleted in 55677a5), so this cannot be re-tested except by rebuilding the old chain; it has no bearing on the new kext, which does not use the framebuffer's range at all.
- Both statements about the Lombard hold regardless: the README-SONICR Lombard observation ("VRAM is little-endian") is about the `Mach64Accelerator` kext that mapped BAR0 itself (lower view), which is the same thing the new kext does.

## 5. What is genuinely unproven (and one new risk)

1. **LOWER_APER_ENDIAN on a Lombard (new, not in 11.3).** MEM_CNTL has two endian fields: bits 27:26 `UPPER_APER_ENDIAN` and bits 25:24 `LOWER_APER_ENDIAN` (diagram, RRG PDF pages 80-81 = printed 4-16/4-17). The NDRV's CRTC programmer `0x10016f50` (funcs.c lines ~11715-11742; `FUN_1000d9c0` calls it) writes its depth-dependent endian value (0 for 4/8 bpp, 1 for 16, 2 for 32) by a byte write to MEM_CNTL byte 3 (`0xb3`), with the field position chosen by which head the instance drives: for the primary CRTC instance (`this+0x61c` == 1; set from the property `my_display`, `'prim'` = 0x7072696d, see `FUN_10004170`) it writes `(x & 0x3f) << 2 | (b3 & 0xf3)` = bits 27:26 (upper); for the **secondary CRTC instance** (`this+0x61c` == 2, `'secd'` = 0x73656364, the container `ATY,264LTProA:Crtc2`) it writes `x | (b3 & 0xfc)` = bits **25:24 = LOWER_APER_ENDIAN**, and `FUN_1000d9c0` first clears those bits for that instance (`b3 & 0xfc`, funcs.c line 7518). The same function also programs the pixel width differently per head (register byte 0x1d bits 2:0 for the primary; a 3-bit field at bits 19:17 of the 32-bit register at offset 0x1c for the secondary, which also sets bit 21), i.e. the instance split is real code, not a labelling artefact. Section 17.4 of the NDRV doc says the panel moves to CRTC2 when an external monitor is attached. So **if a second framebuffer instance runs on a Lombard (external monitor), the lower 8 MB view may be swapped at that instance's depth** and "kernel writes through the unswapped lower view" no longer holds. Whether a Lombard (4c49) actually instantiates the Crtc2 NDRV, and whether the register window inside the lower view (0x7ff800) is exempt from the swap, are **not established**. If the window is not exempt, our `engineEnable` sanity read (BUS_EXT_REG_EN at BUS_CNTL bit 27 and CRTC_GEN_CNTL bit 25, `RageLTEngine.cpp:33-34`) would fail and the engine would refuse to start (loud, safe). If it is exempt, textures and readbacks would be silently byte-swapped (the dangerous case). The G4 stub rig cannot show either (it never sets LOWER; stub MEM_CNTL reads 0x14751a7b: bits 25:24 = 00, bits 27:26 = 01).
2. Which VRAM view the old patched Apple kext actually used on the stub rig (section 4): not established, now irrelevant.
3. Whether stock Apple CPU texture stores on the Lombard are depth dependent (section 3, item 4): inferred only.
4. The stock `ATIRagePro` records the swap mode: `set_display_mode_and_vram` (0x12f44-0x12f98) reads MEM_CNTL (offset 0xb0, `rlwinm 6,30,31` = bits 27:26) and stores 2 (01), 4 (10) or 0 in `this[0x54c]` (-1 when `this[0xcc] != 1`). Nothing inside the kext reads that field (the only other `0x54c` uses are vtable slot loads), so the consumer, if any, is outside the kext. Not established. It is the one trace in the stock stack of the aperture swap mode being propagated.

## 6. What stock does for texture byte order (static)

- There is **no Apple Rage Pro GL driver**: `IOGLBundleName ATIRageProGLDriver` names a bundle that was never shipped (`framework-integration.md`). `scratchpad/stock/gl/ATIRageProGLDriver` is this project's Path-B plugin (strings: `Mach64Accelerator`, `[pathb] z-buffer ...`), not an Apple binary. So there is no stock texture byte-order logic to read; the Lombard's earlier texture results came from our plugin plus the patched kext (above).
- Stock `ATIRageProGA` (the 2D plugin, 0x1ec8 bytes of text) contains **no** byte-reversing instruction (`lwbrx/stwbrx/lhbrx/sthbrx` count 0): it never swaps pixel data itself.
- Stock `ATIRagePro` kext: the only `lwbrx/stwbrx` are register accesses (29 `stwbrx` in the text, all against the register base `this[0x550]`); it has no CPU texture-copy loop (the stock GL `new_texture` body at 0x71e4 is the one the patch overwrote, "broken, panic-prone"); texture and image data go through `IOTransferBuffer` + GART mapping (`map_transfer_to_GART`, `addToGART`) i.e. system-memory transfers. Engine-side host-data endian conversion exists in the chip (`HOST_CNTL.HOST_BIG_ENDIAN_EN`, `SRC_CNTL` bit "aa", RRG 5-34) but the stock kext loads no constant 0x90 (HOST_CNTL) so it does not set it directly (table-driven writes not excluded).
- Net: stock offers no precedent to copy. Its only trace is the swap-mode record in item 4 above.

## 7. Work remaining (small, no G4 live test required)

1. **Guard for LOWER/UPPER_APER_ENDIAN (proposed, small).** At `engineEnable` and at every did-change/wake, read MEM_CNTL (a plain register read; the G4's `chipinfo` already reads it) and log bits 25:24 and 27:26 (a `RAGE_EV_MARK`). If bits 25:24 are non-zero: either refuse byte-image paths (`vramCopyIn/Out`, DMA upload staging) with `kIOReturnNotReady` and say why, or compensate by XOR-ing the transfer flags (01 -> add SWAP16, 10 -> add SWAP32; the table in section 3 gives the algebra: an extra aperture swap composes with the kernel's own swap). Compensation is only valid if the register window is exempt, which is unproven; refusing is the conservative choice. G4 verification: the value reads 00 and the log line appears (read-only); the compensation algebra can be checked on the host with the section-3 model (a 20-line test). No chip write is needed or proposed.
2. **Documentation fixes** (not done here; docs/remaining-work.md and other docs belong to other work): ledger L9 -> "resolved: new kernel owns the byte image, validated on the G4; residual LOWER_APER_ENDIAN guard"; design 3.6 and the O4 row -> point to this note; `memory-map.md` 5c is about the deleted Path-B kext and should say so; `RageStubFB::viewRange` comment ("Apple's kext received the lower view") should carry a "contradicted by the colour test, not established" remark.
3. **Optional, low priority, not recommended now:** a bounded G4 experiment setting `LOWER_APER_ENDIAN` and reading the register window would settle whether the window is exempt. It writes MEM_CNTL on the live chip (user: chip register experiments are lowest priority and may need the user to recover), so it stays queued; the guard in item 1 makes the answer non-critical.
4. The Lombard report bundle (`ragelt-report`) should include `ioreg -l -w0` lines for the framebuffer instances (is there an `ATY,264LTProA:Crtc2` node?) and the MEM_CNTL value from the log line of item 1: that answers section 5 item 1 in one report.
