# Apple's framebuffer for the Rage LT Pro (the NDRV) vs our RageStubFB

Goal (user, Nov 26): better test parity between the G4 rig and the Lombard. Question: do Lombard-only behaviours come from Apple's framebuffer, and should we use it, or make ours behave like it?
Method: static analysis only (Ghidra, PowerPC 32 BE) of Apple's `ATIDriver` NDRV 1.3.42 from the G4's Panther install, container `ATY,264LTPro` (see `tools/ndrv/README.md`). Nothing was run on hardware. Evidence level for every statement below: "static" = read from the decompiled code (function addresses are the Ghidra image addresses of that container); "inferred" = reasoning from it. Not covered: see the end.

## 0. Which driver does the Lombard run?
On Panther the framebuffer is not a kext: `IONDRVFramebuffer` runs an NDRV, preferring the one in the card's Open Firmware node (`driver,AAPL,MacOS,PowerPC`, the ROM copy) and otherwise the file-based one matching `IONameMatch ATY,*`. The file copy on the G4 contains `ATY,264LTPro` (and `ATY,RageLTPro`, `ATY,264LTProA:Crtc2`). **We do not know whether the Lombard runs the ROM copy or this one**; they are probably related but may differ in version. One `ioreg -l -w0` from the Lombard answers it (framebuffer class, `ATY,*` properties, VRAM size, panel properties).

## 1. What the NDRV does (static)
- Entry: `DoDriverIO` (code 0x10005030) dispatches Open 0x100043a0 -> 0x10005440, Close, Control 0x10005de0, Status 0x100061e0, Initialize/Replace 0x10004490, Finalize/Superseded 0x10004c00.
- Registers: always through the chip's **memory-mapped register window inside BAR0** (`aperture + 0x7ffc00`, block 0 at `0x7ff800`; byte-swapped in software = little-endian register access, helper functions 0x10001820/17e0/18f0/1860/1930/18a0). That is also how our kext does it (`fMap + 0x7ff800`), so no difference.
- It moves **PCI BAR2** (config 0x18) to `aperture + 0xfff000` and sets the processor cache mode of the 16 MB aperture to inhibited (mode 1) and of that 4 KB block to 3 (0x1000d2f0). Our kext does not use BAR2 (design: BAR0 window), so this does not change what we map. (inferred: harmless to us)
- Chip init (only when it is not taking over a running instance; flags `ATY,Flags`): PLL registers (index/value pairs 0=0xad, 1=0xd5, 0xd=0x1b, 2=0x3c, 3=0x54, 5=0x4/0x3, then table-driven by `CONFIG_STAT0[2:0]` memory type), then in 0x10016d80: **BUS_CNTL=0x7b33a040, DAC_CNTL=0x82010102, DAC_MASK=0xff, HW_DEBUG=0x08000800, CUSTOM_MACRO_CNTL=0x00200370**; in 0x100177d0 the memory timing: MEM_CNTL (0xb0-0xb3), EXT_MEM_CNTL (0xac, |=0x80000001...), **MEM_BUF_CNTL=0x00382848**, all table-driven by memory type. Engine reset sequence on GEN_TEST_CNTL, FIFO/GUI idle waits (0x310, 0x338) and `BUS_CNTL |= 0x800000`.
- Upper aperture endian (MEM_CNTL bits 27:26): 0 for <=8 bpp, 1 for 16 bpp, 2 for 32 bpp, set per mode. **Same as RageStubFB** (and as design 11.3): the Lombard's byte order question (L9/O4) is answered for the NDRV: the swap alias is selected per depth, the lower view stays unswapped.
- The framebuffer base address handed to WindowServer is in the **upper (byte-swapped) 8 MB** (`0x800000 + offset`, 0x1000d840), like our stub for user tasks.

## 2. Differences that can matter for our driver
**D1. The framebuffer does not start at VRAM offset 0 (static).** 0x1000d900: `offset = 0x200000 mod pitch_bytes`, then raised by whole scanlines until `>= 0x440`. Examples: 1024 px at 16 bpp (pitch 2048) -> 0x800; 1024 at 32 bpp (4096) -> 0x1000; 1280x1024 at 16 bpp (pitch 2560) -> 0xc00. The stub uses offset 0 (`CRTC_OFF_PITCH` = 0x14000000 at 640x480 on the G4). The old notes assumed "Lombard (real framebuffer at 0)" (heap-offset0 note, stubctl): **that assumption is contradicted by the NDRV code**.
**D2. Hardware cursor image lives in VRAM at 0x40..0x440 (static).** Cursor: 64x64, 2 bpp, 1 KB, written to `aperture + 0x40`, `CUR_OFFSET` = 8 (qwords) (+ y-offset), colours in CUR_CLR0/1, position/offset regs 0x6c/0x70, enabled by GEN_TEST_CNTL bit 7 (code 0x100011a0, 0x10000f30, 0x10000d90). The G4 stub has no hardware cursor (WindowServer draws a software cursor). D1 + D2 are one unit: the NDRV keeps `[0, fb_base)` for the cursor.
**D3. Consequence for our allocator (static + our code):** `reserveDisplay` reserves only `[fDisp.base, +size)` and `[0x770000, 0x7ff800)`. With the NDRV's layout the gap `[0, fb_base)` (about 2-4 KB) is free to the allocator, and its **best-fit** policy prefers the smallest gap that fits, so any small client allocation (a few hundred bytes to ~2 KB) lands exactly on the cursor image. Effects: corrupted/garbage hardware cursor, or our data overwritten by cursor shape updates. This cannot happen on the G4 today (base 0). It is a candidate for Lombard-only cursor/texture corruption; **not yet confirmed**. Cheap to fix and test: reserve `[0, fb_base)` (or at least `[0, 0x440)`) always, and make the stub use the NDRV layout so the G4 exercises it.
**D4. Overlay vs hardware cursor (inferred, open):** on the G4 the software cursor is hidden by the overlay (release notes 0.2). On the Lombard the NDRV's hardware cursor is composited by the DAC; whether it shows over the video overlay is not known (the chip's cursor/overlay priority). The G4 cannot show this until the stub has a hardware cursor.
**D5. Chip state the NDRV sets and the stub leaves to the PC BIOS (static vs G4 BIOS state, unmeasured):** BUS_CNTL, DAC_CNTL, HW_DEBUG, CUSTOM_MACRO_CNTL, memory timing/MEM_BUF_CNTL, PLL. BUS_CNTL matters for bus-master DMA (ledger L6: "game's mode switch reinits BUS_CNTL"): the NDRV writes the constant above during init and `|= 0x800000` after engine resets, so **mode changes under the NDRV can re-write BUS_CNTL** (inferred; which paths run on a plain mode switch is not yet traced). Compare with the G4's live values (a register read, proposed below).
**D6. LCD panel (static, not decoded):** the NDRV drives the panel through LCD_INDEX/LCD_DATA (0xa4/0xa8): stretching, power sequencing, `ATY,Panel` properties, DDC/EDID fallback to panel size. The G4's card has no panel; CRT modes only. Any panel-stretch behaviour of small modes on the Lombard (a 640x480 mode stretched by the chip's panel scaler, not by us) cannot be reproduced on the G4.
**D7. Display FIFO (DSP_CONFIG/DSP_ON_OFF) is computed, not tabled (static):** 0x10017ae0 evaluates floating-point formulas from pixel clock, bpp and the memory timing it read back (MEM_CNTL fields). This is the exact source for the open "DSP_ON discrepancy" item; decoding its constants is a bounded follow-up.
**D8. VBL interrupt (static):** the NDRV installs a vertical-blank interrupt service (`VSLNewInterruptService 'vbl '`, CRTC_INT_CNTL). Ours is polled; unaffected so far.

## 3. What did NOT differ
Register access path, BAR0 register window, upper-aperture endian selection, framebuffer visible through the upper aperture, no EDID dependence on our side.

## 4. Not analysed yet
Mode-set CRTC/PLL timing programming (0x100066d0 is only SavePreferredConfiguration; the actual SwitchMode path was not traced), gamma/CLUT, power management/sleep-wake (csCode 0x19 -> 0x1000e770), panel stretch registers, the Crtc2 head, and the ROM copy of the NDRV (not available; the Lombard's `ioreg` plus a dump of the OF property would give it).

## 5. Options (decision input)
1. **Use Apple's NDRV on the G4**: give the G4's card an `ATY,264LTPro` identity so `IONDRVFramebuffer` loads the file copy. Highest parity (same code as the Lombard, if it runs the file copy), but the card has no Open Firmware node/properties the NDRV expects (`ATY,Flags`, `ATY,MEMSIZE`, `driver,ist`, 'my display' tags...) and the NDRV would reinit the chip over our BIOS-posted state. Feasible only after tracing what it reads; risky (crash = reboot, 2-3 min on the G4).
2. **Make RageStubFB behave like the NDRV** where it affects our driver: framebuffer at the NDRV's offset with the cursor block below it (cheap, reproduces D1/D3 on the G4), hardware cursor (D2/D4), and optionally the same chip init constants (D5). Each is testable on the G4.
3. Do 2 for D1-D3 now (they are cheap and may explain Lombard behaviour), and keep 1 as a later experiment.

## 6. Implemented on the G4 rig (Nov 26, option C)
- `RageStubFB` now places the frame buffer at Apple's NDRV offset (`rm_fb_offset`, `rage_modeset.h`; property `RageNdrvLayout`, boot-arg `rage_fb0=1` restores offset 0). The ROM's boot mode is moved at start (640x480 15 bpp: 0x700), every mode change programs the offset in `CRTC_OFF_PITCH`, and `getApertureRange` starts at the frame (WindowServer was given "frame at +0x700"; the VRAM range still starts at 0). The boot-time replay check accepts either offset.
- The kext (`reserveDisplay`/`modeWillChange`) reserves `[0, fb_base)` whenever the base is non-zero.
- Proof that D3 was real: with the stub in the NDRV layout and the reservation removed, `tools/ragegl/fb_layout` shows the allocator handing out 8-byte blocks from offset **0x0** upward, straight over the cursor image at 0x40..0x440 (64/64 blocks below the frame end). With the reservation: lowest allocation = frame buffer end.
- Measured bases on the G4: 640x480 15 bpp 0x700; 1024x768 15 bpp 0x800; 1024x768 32 bpp 0x1000; 1280x1024 15 bpp 0xc00 (all equal to the NDRV formula). Release kext + bundle at all of these: `fb_layout` passes, `gl_suite` 291/291 (overlay and RAGE_GL_OVERLAY=0 at 1024x768), `ovl_gate` 16/16 (15 and 32 bpp) and 8/8 (quad).
- Not done: a hardware cursor in the stub (D2/D4), the NDRV's chip-init constants (D5), panel handling (D6).

## 7. The stub now owns the memory below the frame buffer; coexistence test (Nov 26)
- `RageStubFB` fills VRAM `[0, fb_offset)` with a position-dependent canary at start and after every mode change and sets `CUR_OFFSET` = 8 (cursor image at 0x40, hardware cursor still disabled): the same memory the NDRV owns. `cursor_guard` (root) counts the bytes that no longer hold the pattern (`rage-cursor-check`; `cursor_guard fill` refills it).
- Positive run, release kext + bundle, 1024x768 15 bpp, 1024x768 32 bpp, 1280x1024 15 bpp: `gl_suite` 291/291 (overlay and `RAGE_GL_OVERLAY=0`), `ovl_gate` 16/16, `fb_layout`: the guard reports the block intact after each.
- Negative control (kext built without the low reservation, `fb_layout w` writing over the blocks it gets): 64 blocks from offset 0x0, **1976 bytes of the canary overwritten**, guard FAILED. The same test with the reservation: blocks start at the frame buffer end, guard passed.
- Honest limit: `gl_suite` alone would NOT have caught the missing reservation (its allocations are all larger than the 2-4 KB gap, so best-fit never picks it); only small allocations do. The Lombard hits it only if some client (a game, GLEngine, Apple's own code) makes small VRAM allocations, which `fb_layout w` models.

## 8. Real applications on the stub (Nov 26): Chess black at 32 bpp
Exercise (`tools/rig/layout_exercise.sh`: Atlantis, Flurry screensaver, Chess, Sonic R 120 s without input so the title's idle timeout starts the race demo), release kext, 1024x768, canary intact after every app at both depths, no crash logs, kext stayed loaded.
- **15/16 bpp:** all four render; Chess correct once its window is on the Rage display (its saved frame `1540 -248 ...` put it on the GeForce under the new arrangement; the script now resets it). Sonic R demo ran.
- **32 bpp:** Sonic R, Flurry render; **Chess shows a black 3D view** (`NSOpenGLView lockFocus` logs `invalid memory allocation` = `kCGLBadAlloc`).
- **Cause (measured, `RAGE_SURF_LOG=1`):** Chess opens two GL contexts: 740x680 (target 32 bpp + Z about 3 MB: ok) then 630x418 (fails, no space; the 16 bpp fallback fails too). With the scanout at 800x600 32 bpp (more free VRAM) Chess renders correctly. Free VRAM at 1024x768x32 is about 4.4 MB (usable end 0x770000 minus the 3 MB scanout). Unrelated to the memory layout: the canary was intact.
- **Second symptom, cause found:** the black 740x680 area. `RAGE_PTRACE` shows the first context's window (388/289 at 5,50) gets exactly one present, and its visible-rect query returns -1 because the window is **not in the on-screen window list** (never shown). `present_rects` treated -1 as "CGS failed, keep the full rect" and blitted the whole 740x680 to the scanout; the window server never repaints that area, so it stays.
- **Fix (Nov 26, gldriver):** `mach64_cgs_visible_rects` returns **-2** for "window not on screen" and the driver presents nothing for it (the idle-repaint thread retries every 100 ms, so a window that appears a moment later still gets its contents). When a surface build fails, the driver frees the colour/Z blocks of the OTHER windowed contexts of the process whose windows are off screen (`evict_offscreen`; registry of contexts) and retries; an evicted context is rebuilt on its next draw/present (`mach64_mode_check`), and the repaint thread skips contexts with no surface. Not done at the first off-screen present on purpose: Chess's real view also reports "not listed" on its first present, and releasing then would lose its first frame (Chess only redraws on events).
- **Verified (G4, release kext, new bundle):** Chess at 1024x768 32 bpp: board/textures/lighting correct, no stale surface, clipped correctly by an overlapping window; `gl_suite` 291/291 at 32 and 16 bpp, `ovl_gate` 16/16, `fb_layout w` + `cursor_guard` pass; full exercise at 32 bpp (Atlantis, Flurry, Chess, Sonic R 120 s demo at 14.3 presents/s): guard intact after every app, no crash logs.
- **Unexplained:** one capture taken right after switching 32 -> 16 bpp showed black and white patches around the Chess window; an immediate rerun at 16 bpp was clean. Not reproduced, cause not established.
- Debug aid: `RAGE_SURF_LOG=1` makes the GL driver print every surface build to stderr.

## 9. Known limitation: translucent windows over a GL window show their backing (white box)
Seen with the Speech Recognition feedback window (the circular "Esc" microphone, CGS window 586/761, 94x94, level 3) in front of a Chess GL view: the circle is surrounded by a white square. Not a Chess alpha bug.
- `tools/ragegl/windump` (mask 8) shows what the window server reports for each on-screen window: the speech window's **shape** is the full 94x94 rectangle (not round) and its **opaque shape** is empty; the menu bar, Dock and similar translucent windows also have empty opaque shapes, while the Terminal and Chess windows have non-empty ones (`CGSGetWindowOpaqueShape`; `CGSGetWindowAlpha` is 1.00 for all, so it is no help). `CGSWindowIsAccelerated` as declared crashes (signature guessed wrong).
- Cause (inferred, not separately tested): our GL pixels go straight to the scanout, outside the window server's backing stores. When it redraws the translucent window it composites it over the Chess window's own backing (white) and writes the whole rectangle to the screen, overwriting our pixels; `present_rects` excludes every window in front (full frame rect), so the corners are never repainted by us.
- No clean fix: the driver cannot read the translucent window's per-pixel alpha, and painting GL under it would erase it until its next redraw. A workaround was considered (re-blit GL pixels inside a translucent window's rectangle only where the screen shows the backing colour: removes the white corners, but pure-white pixels in the window would turn into GL pixels, anti-aliased edges keep a white halo, the backing colour has to be sampled, and it costs a CPU read/write per present). Decision (user, Nov 26): **not implemented; documented as a limitation.** It applies to any translucent window (speech feedback, Dock shadow, menus) over a GL window.

## 10. Apple's display-FIFO formula decoded (NDRV function 0x10017ae0; static, Nov 26) - resolves D7
Constants read from the unpacked data section (data base 0x1001a930): 64.0, 4096.0, 32.0, 0.99999, 3.0, 2.0, 0.5. Lookup tables: memory type -> group `memtype >> 1` (`0x1001da4a`: 0,0,1,1,2,2,3,3); latency base `{8,6,9,8}` (`0x1001da5a`) and page-fault extra `{3,2,2,1}` (`0x1001da62`), both indexed by `(group >= 2)*2 + (vram_mb >= 2)`; bits-per-pixel by CRTC_PIX_WIDTH `{0,4,8,16,16,24,32,0}`. Inputs read from the chip: CONFIG_STAT0 (0xe4) memory type, CRTC_GEN_CNTL byte 0x1d pixel width, MEM_CNTL bytes 0xb1/0xb2 (TRP, TRCD, TCRD, TRAS, same fields as ours), PLL registers for XCLK and VCLK. `vram_mb` is a driver field at +0x524 shifted right by 20 (inferred to be the VRAM size).
- `x` = 64 * XCLK / (VCLK * bpp) (xclks per quadword; the same ratio as the X.Org mult/div).
- `prec = clamp(max(bitlen(int x) - 3, bitlen(int 32x) - 5), 0, 7)` (same as X.Org's loop), `depth = min(32, int(2^(prec+5) / x))` (**X.Org fixes 32**), `OFF = int(int(x*(depth-1) - 0.99999) * 2^(6-prec))`, `XCLKS_PER_QW = int(x * 2^(11-prec))`.
- **`DSP_ON = int(3 * max(pf, ras) * 2^(6-prec))`** with `pf = trp+trcd+tcrd+2+extra`, `ras = trp+tras+2`. X.Org's formula adds `max(on, ras*..) + 2*ras*.. + pf*..`, so it gives roughly twice as much.
- `DSP_CONFIG = XCLKS | (latency & 15) << 16 | prec << 20 | (old & 0x8000)`, `latency = latency_base + 2`; `DSP_ON_OFF = ON << 16 | OFF`.
- Not modelled (flagged paths): the second head, a 4096/n scale factor (display property 0x10), a cap of 24 for display mode id 0x50.
- Integer replica: `rage_dsp_apple_calc` in `rig/stubfb/rage_modemath.h`, compared with ours in `hosttest/modemath_test.c` (passes). **Not used by the stub.**
- **Result for the one hardware calibration point (640x480 15 bpp, 25.175 MHz, ROM 0x004807f7 / 0x009c07b0):** Apple's formula gives precision 4, DSP_OFF **1968 (exact)**, XCLKS 2038 (ROM 2039) and latency 8 (with memory type 0-3; type 4 gives 10), but **DSP_ON 108** (ROM 156, ours 192). So DSP_ON is NOT explained by the formula: the ROM's 156 corresponds to `max_ras` 13 where this card's MEM_CNTL gives 9. The PC BIOS evidently uses a different memory model than Apple's code. Across the rig's modes Apple's DSP_ON is about 0.56x ours at 16 bpp and 0.57x at 32 bpp (table in the test output), OFF within about 1-2%.
- **Which memory type the card has is unknown:** the stub hard-codes memtype 4 / 8192 KB (`RageStubFB.cpp`, `rm_plan_mode(..., 8192, 4, ...)`) instead of reading CONFIG_STAT0 as Apple does; the latency (and page-fault extra) differ between the two assumptions. Reading CONFIG_STAT0 on the G4 is a safe register read and is the next step for this item.
- Not decided: whether a smaller DSP_ON is safe. The ROM point (156) lies between Apple's (108) and ours (192); only the ROM point has hardware-proven stability at 25.175 MHz.

## 11. Hardware cursor in the stub (Nov 26)
`RageStubFB` now implements `setCursorImage`/`setCursorState` and answers `kIOHardwareCursorAttribute` ('crsr'), on the Apple NDRV layout: 64x64, 2 bpp, 16 bytes per row, first pixel in the low bits of the first byte (Programmer's Guide 6.4.3), image at VRAM 0x40 (CUR_OFFSET 8 qwords), colours CUR_CLR0 = black, CUR_CLR1 = white, enable = GEN_TEST_CNTL bit 7. **Opt-in** (Info.plist `RageHwCursor`, default false; boot-arg `rage_hwcur0=1` forces it off); only with the NDRV layout (`RageNdrvLayout`).
- Register offsets: the RRG's "0_34" notation is a DWORD index, so GEN_TEST_CNTL is byte offset 0xd0 (0x34 is MEM_ADDR_CONFIG). My first build wrote bit 7 of 0x34; the write was inert (bit does not stick, still 0x202) but it was a wrong-register write, fixed before anything else was concluded.
- Conversion: `convertCursorImage` (IOGraphicsFamily 0xb7a0, disassembled) FAILS in indexed (8 bit) mode on any pixel with partial alpha, and the system arrow is anti-aliased. Asked for 32-bit ARGB it works (32x32 arrow, 103 opaque pixels, 48 white); the stub quantises (alpha >= 128 opaque; luminance >= 128 white) and packs. The packed image is published as `RageCursorArt` (ioreg): a correct black arrow with white outline.
- **Panic found:** if the stub advertises a hardware cursor and `setCursorImage` fails, IOFramebuffer is left with neither cursor working and its software-cursor blit (`cursorBlitProc`, IOGraphicsFamily 0x7... via IOHIDFamily) dereferences a bad pointer (DAR 0x4A028218) as soon as the pointer enters the Rage display (user: it happened on moving the mouse there). Never advertise 'crsr' unless the image conversion is known to work, hence opt-in.
- Position: negative x/y saturate to 0 and use CUR_HORZ_VERT_OFF / CUR_OFFSET += 2 qwords per row (guide recipe). `tools/rig/cursor_walk.c` warps the pointer over the Rage display (centre, edges, corners) and the stub's `rage-cursor-regs` property returns the registers: GEN_TEST_CNTL 0x80 while the pointer is on the Rage, 0 off it; CUR_POSN/CUR_OFF/CUR_OFFSET match the expected clipped values at every point (top edge: CUR_OFFSET 0xe = 8 + 2*3 rows, CUR_OFF vert 3). No panic with the pointer on the Rage; canary guard passes (the image area is excluded once a cursor is loaded).
- Not yet verified: that the cursor is VISIBLE on the screen and over the video overlay (needs eyes on the Rage monitor), and the interaction with the GL driver's direct-to-scanout windows.

## 12. Chip configuration: the card against Apple's NDRV init constants (read-only, Nov 26)
`tools/rig/chipinfo` (stub property `rage-chipinfo`, reads only) on the G4's card at 640x480 15 bpp after the stub's mode set:
`CHIP_ID dc004c49  CONFIG_STAT0 00e000b4  CONFIG_STAT1 00000000  MEM_CNTL 14751a7b  MEM_BUF_CNTL 00382848  BUS_CNTL 7b330101  DAC_CNTL 8601010a  HW_DEBUG 48803800  CUSTOM_MACRO_CNTL 003c0171`
- **Memory type:** `CONFIG_STAT0 & 7 = 4`, so the stub's hard-coded `rm_plan_mode(..., 8192, 4, ...)` equals what Apple's code would read from the chip (Apple's table `da4a[4]` = group 2). With this card the Apple formula's latency is 8+2 = 10 (not the ROM's 8) and its page-fault extra 1. Reading the register in the stub would be equivalent on this card and correct on others; not changed (no behaviour change).
- **MEM_CNTL** 0x14751a7b = the ROM calibration value 0x10751a7b plus UPPER_APER_ENDIAN (bit 26) set by the stub; the timing bytes (0xb1 = 0x1a, 0xb2 = 0x75) that the DSP formulas use are the same. **MEM_BUF_CNTL** equals the NDRV constant (0x00382848).
- **Differences from the NDRV's constants** (XOR): BUS_CNTL 0xa0330141 -> low half only: 0xa141 (NDRV 0xa040, card 0x0101), DAC_CNTL 0x0400000 8 -> 0x04000008, HW_DEBUG 0x40803000 (NDRV 0x08000800, card 0x48803800), CUSTOM_MACRO_CNTL 0x001c0201 (NDRV 0x00200370, card 0x003c0171). These are the PC BIOS's POST values against Apple's init values; the register reference's field tables give no bit positions, so which named fields differ is NOT established here. Tentatively (positions taken from Linux's atyfb header, unproven): the NDRV's BUS_CNTL has bus-master disabled (bit 6) and PCI read retry on (bit 13) where the card's has neither - consistent with the NDRV not using bus mastering while this project's kernel driver enables it itself. Nothing was written: no differing register is known to cause a problem (the kernel driver's DMA, the overlay and the GL tests run on these values).
- **Display FIFO (item from section 10), evaluation:** the formula is decoded and the card's memory type is known (4). At the only hardware-proven point (640x480 15 bpp, 25.175 MHz) Apple's formula gives DSP_ON 108 against the ROM's 156 and ours (192); every other rig mode would get ~0.56x our DSP_ON. There is no underrun status register in the documentation, so a smaller DSP_ON can only be judged by eye (tearing/flicker/garbage) in a hold with a mode that is FIFO-limited (1024x768 at 32 bpp, 65 MHz). Not enabled; needs the user's go-ahead and eyes on the monitor.
