# Texture DMA upload in the standalone driver (design, Nov 25)

Builds on the plugin-era measurements in `dma-upload-design.md` (system transfer: `BM_SYSTEM_TABLE` 0x1bc, descriptors `{VRAM offset, system physical address, count <= 4096 | EOL, 0}`, no draw engine, no FIFO; 112 KB in 1-2 ms with the CPU free; CPU cost of filling an uncached buffer 0.49 ms, of a cached one 0.22 ms vs 3.5 ms for CPU stores into the VRAM aperture) and on the serial kernel-owned pattern of design 11.16 / `dma-async-measurement.md` / `bus-master-ring.md` (kernel owns the memory and validates every request, submit returns after the kick, `idleWait()` precedes every other engine use and every CPU VRAM access, bounded wait with engine reset on timeout, a second submit waits for the first). No threads, no interrupts (O6: no completion interrupt exists for the GUI master; the system transfer's is untested and not needed).

## Mechanism
* `RAGE_GL_VRAM_WRITE` (selector 10) today: 16 KB chunks, `copyin` to a kernel buffer, then `vramCopyIn` stores every word through the **uncached VRAM aperture** (about 32 MB/s of CPU time). New: when the length is >= 8 KB and DMA upload is available, the same call copies the user data into a **kernel-owned, physically contiguous, cached staging buffer** (1 MB, falling back to 512/256/128/64 KB), applies the byte swaps of `flags` in place (cached stores), writes back the cache (`dcbf`) and kicks the system transfer, then **returns**.
* Per chunk: `xferReserve()` (stage lock, waits for the previous transfer) -> `copyin` straight into the stage (outside the device lock) -> `xferKick()` (device lock: ownership check by `rage_vram_owns`, `idleWait()`, descriptors, kick, unlock). Lock order is stage lock -> device lock everywhere.
* Kick: save `BUS_CNTL`, enable bus mastering (`BUS_MASTER_DIS` clear, `BUS_EXT_REG_EN` set), write `table_phys` to `BM_SYSTEM_TABLE`. The staging memory, the descriptor table and both physical addresses are kernel-owned; a client never sees an address; the destination range is checked against what the client owns before anything is written.

## Fencing (the correctness question)
`fDmaPending` now means "anything in flight" (GUI stream **or** system transfer; the GUI-stream-specific meaning moves to `fGuiPending`). `dmaWait()` first finishes a pending transfer, so every path that already drains before using the engine or the aperture (`idleWait`, the DMA submit's own wait before its kick, the PIO paths, `vramCopyIn/Out`, present, fill, clear, mode change, stop) automatically waits for the upload. A draw that samples the texture is built (CPU) while the transfer streams and waits for it only at its kick. Completion = `BM_COMMAND == 0x80000000` and `BM_SYSTEM_TABLE` at the table end **and** the last word of the destination read back from VRAM equals the last word staged (a data-level proof that the transfer landed, not only that descriptors were consumed). `BUS_CNTL` is restored exactly as found after completion (the GUI stream's restore cannot cut a transfer short because a transfer is always finished first).

## Failure and ownership
* Timeout (bounded spin): log, `eng_reset`, restore `BUS_CNTL`, mark DMA upload disabled for the rest of the session; the CPU path is used from then on.
* No staging memory, `BUS_CNTL` surprises, physical address >= 2 GB, or length < 8 KB: the CPU path (unchanged).
* A client that dies mid-transfer leaves nothing behind: the memory is the device's, the next `dmaWait` finishes the transfer, the destination range is freed by `releaseOwner` as before (the in-flight bytes land in memory nobody samples; the next allocation overwrites them, and the allocation's own upload first waits for the transfer).
* Two clients: the stage lock serialises their fill/kick; transfers are serial (one in flight).

## Tests (before anything is called done)
1. Host-free kernel test `tools/ragegl/xfer_test`: sizes 4 KB..1 MB, all flag values, odd offsets, read back through `vread` and compare every byte; ownership refusal (a range the client does not own is refused with no hardware access); 2 clients writing concurrently; upload immediately followed by a draw that samples it (the suite's texture tests cover this; also run with DMA upload forced on/off).
2. Timing: CPU time in the `vwrite` call, DMA vs CPU path (`RAGE_GL_CONFIG` key 2 switches DMA upload), for 16 KB / 256 KB / 1 MB.
3. Gate: `gl_suite` 290/290 and `gl_probe` 128 pass / 1 fail with DMA upload on.

## Results (Nov 25, MDD G4, `tools/ragegl/xfer_test`, kernel event marks 0xd0070000/0xd0071000)
* Correctness: `xfer_test` ALL PASSED - 8 sizes (4 KB .. 1 MB) x 4 flag values, bytes compared with the contract computed in user space (not with the kernel's own inverse), the CPU path and the DMA path give identical bytes, refusals (unowned range, past the allocation end, bad flags, bad length) change nothing, 4 clients (3 forked + parent) uploading 256 KB 60x each with exact readbacks. Unaligned (+4) destinations and < 8 KB use the CPU path by design.
* Proof the DMA path runs: 237 kicks logged in that run (staging 1 MB at a valid physical address, table in its own page), 0 errors (`0xd0072000`/`0xd0073000`); 52 more kicks during one `gl_probe` run (27 KB flags-1 uploads).
* CPU time inside the upload call (20 repetitions): 16 KB 0.60 -> 0.14 ms (4.3x less); 256 KB 8.5 -> 2.2 ms (3.9x); 1 MB 34 -> 9.9 ms (3.4x). Upload + fence back-to-back (engine rate, no overlap): 256 KB 7.6 ms (35 MB/s), 1 MB 31 ms. First measurement with a 256 KB stage gave only 34 -> 24 ms for 1 MB because every 256 KB chunk waited for the previous transfer before the stage could be reused; the stage is now 1 MB (the largest single upload), no double buffer needed.
* Gates with DMA upload on: `gl_suite` 290/290 (rebuilt from scratch), `gl_probe` 128 pass / 1 fail (ARB fragment program, deferred).
* Not done / not claimed: no measurement of a real application's frame time (Sonic R textures load at level start); the CPU still spins in `xferWait` when a draw needs the texture before the transfer ends (bounded); G3 (Lombard) numbers; the 16/24 bpp display modes.
