# B1b: stock-compatible 2D context client (type 2) -- implementation plan (Nov 26)

Inputs: ga-2d-client-decode.md (ABI), quartz-acceleration-study.md (CoreGraphics drives the plugin via IOKit IOPSAllocateBlitEngine and MPHW*; stock plugin declines memory-to-screen 0x2000), memory-map.md and rage_guard.h (containment rules E1: a client never sets an address, scissor, pixel-width or trigger; kernel owns them).
Scope of the first release: display destinations only (stream ops 0x09 CopyRegion and 0x0d Copy, plus Fill/SolidLines/SolidScanlines with a solid source); no VRAM-backed surface table (surface-mode 2D is out). Memory-to-screen flush is B1g (separate).

## Steps (each is testable before the next)
1. **2D stream validator** (`common/rage_2d_guard.h`, header-only, host-tested like rage_guard.h). The stock stream carries raw (reg,val) pairs including DST_Y_X 0x10c, DST_HEIGHT_WIDTH 0x118 (trigger), SRC_Y_X 0x18c, SRC_WIDTH1 0x190, line regs 0x120-0x12c, DST_CNTL 0x130, SRC_CNTL 0x1b4, PAT_REG0/1, DP_BKGD/FRGD/MIX/SRC, CLR_CMP and pseudo-register 0x1fc. The validator parses packet headers (op<<24 | dword length), handles ops 0x01/0x02/0x09/0x0d in the kernel, and for the raw pairs: allow-list the 2D registers, refuse everything else (and 0x100/0x2d0/0x2a8/0x2b4/0x180, which the kernel injects), track the pending rectangle and clamp destination and source rectangles to the display extent before a trigger is written, bound the total length (stock: 0x4000). Register bit layouts are read from the RRG diagrams, not from memory.
2. **Engine back end**: submit the validated pair list through the existing engine path (serial, kernel-owned, FIFO-wait, idle-wait per docs 11.16); kernel prepends 0x100/0x2d0/0x2a8/0x2b4 for the display (from the mode the kext already knows).
3. **Class chain**: a class literally named `ATIRagePro` (the plugin's Start does IOObjectConformsTo(accel, "ATIRagePro") and returns 0x2c7 otherwise; setName is not enough). On the G4 and the Lombard stock `ATIRagePro.kext` is not loaded alongside ours (the installer sets it aside, O7).
4. **Loader wiring**: `IOCFPlugInTypes ACCF0000-0000-0000-0000-000a2789904e -> ATIRageProGA.plugin` in our personality, copied onto the framebuffer in publishFramebuffer together with IOAccelTypes/IOAccelIndex/IOAccelRevision=2. On the G4, RageStubFB must publish the same (it has index 0, revision 2, no IOCFPlugInTypes today).
5. **Type-2 user client** `RageLT2DClient` (newUserClient type 2; types > 2 return 0xe00002c2): selectors 0 set_surface (display ids only; surface-backed mode returns 0x2c2), 1 get_config ((0x04000000, 0)), 3 swap_surface, 4 scale_surface, 5/6 lock/unlock_memory, 7 finish; 2 and 8-15 return the stock error codes; 16-18 are NOT implemented (unrestricted register window). Client memory: type 0 = command buffer + doorbell (each map submits the pending stream and returns a fresh buffer; fixed ring of descriptors because leak-vs-coalesce of repeated maps is not established), type 1 = context buffer.
6. **Context ownership**: the A5 decision (user, Nov 26): one current-context pointer shared with the GL client, replay-from-shadow on switch (stock's model). First build WITHOUT extra save/restore beyond that; test for cross-client state leaks (2D during a running GL app) and measure the cost before adding any.
7. **Rig**: the plugin's Personality says IOProviderClass IONDRVFramebuffer, RageStubFB is not an IONDRVFramebuffer, so IOFindPlugIns may not match it. Whether matching is by metaCast is NOT established. Options: (a) a patched copy of the plugin's Info.plist with IOProviderClass IOFramebuffer (a change to an Apple file under /System/Library/Extensions: needs a backup and the user's decision, so it is the one item here that is not autonomous; USER APPROVED Nov 26: if a plist edit is needed it may be made for experimentation, with a backup of every edited stock file taken first and recorded here; making it permanent is a later discussion), or (b) make RageStubFB subclass IONDRVFramebuffer. Decide after step 5 shows what the loader does.
8. **Verification on the G4**: (i) loader: the plugin loads for the Rage display (registry/vmmap of WindowServer shows the plugin and a type-2 connection); (ii) Quartz fills/copies on the Rage display (scrolling a window, Terminal scroll, fills) produce correct pixels (screencapture) and the engine counters show blit/fill activity; (iii) timing: CPU time and elapsed time for large scrolls with the client versus software fallback; (iv) GL running alongside (Atlantis + window scroll) shows no state leaks; (v) mode change and process-death cleanup; (vi) the whole suite still passes (gl_suite 291).

## Risks
* A bad 2D client can corrupt the Rage display or wedge the engine; the Rage is the secondary display on the rig, and recovery is a reboot (2-3 min); an engine wedge from bad bus-master state is the known one (11.16).
* The plugin ABI is decoded statically; nothing here has run. Struct fields marked "not established" in ga-2d-client-decode.md (lock out1, get_config +0x9c, set_surface mode bits) must be handled conservatively and observed.

## Result (Nov 26, night): speed of the 2D path vs the CPU path (B1g-2) and GL alongside (A5)
Tool: `tools/ragegl/twod_bench` (release kext; 640x480x16, GL client and 2D client open together, WindowServer's own client also open). Hardware = plugin-style streams through the type-2 client, each buffer followed by finish() (so validation, per-op engine programming, idle wait and the doorbell syscalls are all included). CPU = the GL client's VRAM write/read (kernel CPU copy through the aperture, measured 44 MB/s write, 7.5 MB/s read+write) on a scratch area. The CPU proxy carries a syscall cost of about 70 us per call that Quartz writing the mapped framebuffer would not pay, so the small-size rows exaggerate the hardware advantage.

| size | HW fill 1 op/buf | HW fill 32/buf | CPU write | HW copy 1 op/buf | HW copy 32/buf | CPU read+write |
|---|---|---|---|---|---|---|
| 16x16 | 88 us | 26 us | 79 us | 90 us | 28 us | 220 us |
| 64x64 | 90 us | 48 us | 184 us | 100 us | 59 us | 1070 us |
| 128x128 | 172 us | 131 us | 714 us | 202 us | 160 us | 4180 us |
| 256x256 | 501 us (249 MB/s) | 461 us | 2854 us (44 MB/s) | 593 us (211 MB/s) | 552 us | 16.7 ms (7.5 MB/s) |
| 512x384 | 1.38 ms (272 MB/s) | 1.34 ms | 8.5 ms | 1.63 ms (230 MB/s) | 1.59 ms | 50 ms |

- Hardware fills run at 250-280 MB/s and copies at 210-235 MB/s for large rectangles: about 6x the CPU write rate for fills and about 30x the CPU copy rate (VRAM reads are the CPU's problem). Per-op overhead is about 40-85 us with one op per buffer (what the plugin sends) and about 25 us batched.
- Break-even against a direct CPU store at 44 MB/s: about 45x45 pixels for fills (one op per buffer), about 18x18 for copies. Below that the CPU path is faster; the plugin has no say in it (CoreGraphics decides which regions go to hardware).
- Not yet measured: the real WindowServer flush with 2D on vs off (an A/B needs a WindowServer restart per side). Quartz sent only 13 ops for a window drag and resize, so the window-level difference is expected to be small; the table is the answer to "is the hardware path faster".
- A5 coexistence: `gl_suite` 291/0 while `twod_bench` ran concurrently from another process (2D and GL clients both using the engine, WindowServer's client also open); every op programs the full engine context, so interleaving costs only the per-op overhead above. 0 refused buffers.
- Bug found and fixed by the leak check: `RageLT2DClient::clientClose` did not `terminate()`, so each closed client stayed alive (40 instances after about 36 short opens, with their buffers). Fixed; instance count returns to 1 (WindowServer's).
- `twod_test` needs the debug kext (it reads the scanout through `RAGE_GL_SCANOUT_READ`, `tools/rig/redeploy.sh`); on the release kext it stops at "scanout read failed", which is expected.
