# Vertex DMA for Path B: findings and proposed design (Nov 20, NOT implemented)

Goal (user, Nov 20): lift the ~311-triangle-per-frame cap (`gld_render.c` "batch full ... DROPPING triangle"; measured 22% / 61% / 79% of 400 / 800 / 1500 triangles lost).

## Findings (static, stock kext)
* `IOATIRProShared::new_vertex_buffer` (0x10618) only allocates a wired, GART-mapped `IOBufferMemoryDescriptor` and an `IOVertexBuffer` record; `delete_vertex_buffer` frees it. **Nothing in the kext reads a vertex buffer to draw**: the engine is driven only by PIO `{reg,val}` writes through `submit_buffer` (`start_engine` has zero callers) and the kext never programs a bus-master register (a scan for `BM_GUI_TABLE` 0x1b8, `BM_SYSTEM_TABLE` 0x1bc, `BM_COMMAND`, `BUS_CNTL` constants finds only unrelated hits in `build_swap`/`stop`).
* So a "GART vertex-buffer DMA path through Apple's kext" does not exist; the DMA must be ours.
* The per-frame cap is the plugin's own: the PIO body is 4 KB (`ctx->fb`, 1016 dwords at 4 KB; this rig reports cap 16376 / batch limit 8188 dw), the plugin drops overflow instead of flushing because a 2nd same-context type-1 drain is a no-op (accel[0x74] latch, `dma-upload-design.md` section 7).

## What can work
Bus-master GUI stream from system memory (`BM_GUI_TABLE` 0x1b8, Programmer's Guide 8.10; prototyped and verified in `tools/mach64_bmupload.c`: 41 MB/s, 0 wrong pixels, register-write stream through the DMA FIFO). Triangles become register writes in a physically contiguous uncached buffer (Path A kext: 128 KB command buffer + 16 KB ring) instead of PIO pairs, so one frame can hold ~5x more than the PIO body, chunked per 128 KB, with no dependence on Apple's drain.

## Hard problems
1. **Exclusion.** The GUI-path stream shares the register FIFO/draw engine with every other client (WindowServer 2D through Apple's drain, lock `accel[0x544]`). A user-space kick is outside that mutex.
2. **Ordering with the PIO stream.** State (Z, blend, ...) and the deferred clear travel in the PIO drain; the DMA stream must run after them and complete before the present/swap blit and the tail reset.
3. **One drain per frame** (latch) is unchanged for the PIO part.
4. Hardware risk: a bad table/address DMAs over RAM; a wedged engine needs a reboot.

## Measurements (Nov 20, MDD, `tools/mach64_bmidle.c`; same stream as the verified `mach64_bmupload`)
1. **GUI_ACTIVE covers the whole GUI bus-master stream once it has started**: GUI_ACTIVE stays set for the whole transfer (about 3,950 tight polls, 0 -> 1 -> 0 with no dips) and the image is complete when it falls.
2. **But it can read 0 for about a microsecond after the kick**: with a read immediately after the kick write, the first sample was idle in 13 of 100 runs (the stream then completed correctly); with a ~1-2 us gap (a `gettimeofday` call) 0 of 300 runs saw it. So "wait for GUI idle" right after the kick is a race. This kills the earlier idea of using the `submit_buffer` wait before the `SCALE_3D_CNTL` write as the completion fence: nothing guarantees enough delay between the kick pair and that write.
3. **Robust completion: `BM_GUI_TABLE` has reached the table end (`ring + 16 * ndesc`) AND GUI_ACTIVE is low**: 100/100 runs, every pixel correct; polling `BM_GUI_TABLE` during the stream is harmless. Without any register reads (kick, wait 50 ms): 100/100 correct.
4. **Packet encoding for 3D registers is already proven**, by the Path A kext (`docs/re-notes/bus-master-ring.md`, `tools/mach64_ringtest.c`): a stream of `DMAREG(reg) | ((n-1)<<16)` headers + values (`DMAREG(r) = r>=0x400 ? (r-0x400)>>2 : (r>>2)|0x100`), including the 3D state and vertex registers, drew a gouraud triangle through the kext's own `submitCommandBuffer` (covered=507, R/G/B balanced). One descriptor holds at most 4095 bytes (use a 4092 stride, all with HOLD_OFFSET so the parser sees one continuous stream, EOL on the last). Finish the stream with a `DMAREG(SRC_CNTL)` zero terminator.
5. **Path A's `submitCommandBuffer` is the template** for the kernel code: save `BUS_CNTL`/`SRC_CNTL`/`BM_GUI_TABLE`, wait idle, set `BUS_CNTL` bus-master, `BM_GUI_TABLE_CMD = ring`, `SRC_CNTL = BM_ENABLE|BM_SYNC|SYSTEM_TO_REG`, write `DST_HEIGHT_WIDTH = 0` to kick, wait, restore. Today it assumes it owns the engine (no lock shared with Apple's kext).

## Revised design: a DMA submit selector INSIDE Apple's kext (user-approved direction, Nov 20)
Why in the kernel: exclusion. The handler takes `accel[0x544]` (the mutex that serialises GL and 2D drains) so it cannot interleave with WindowServer's register programming, it validates physical addresses itself, and it can poll `BM_GUI_TABLE` + GUI_ACTIVE (measurement 3) instead of relying on a racy fence. It is also not subject to the one-drain-per-frame latch (it is a separate selector, not the type-1 drain).
* **Selector**: repurpose/add one user-client method (the precedent: `new_texture` -> VRAM memcpy, selector 10, 19 hand-assembled instructions). Input: `{ u32 byte_count }` plus the stream in a buffer the kext can address; the simplest first version copies the stream from the caller's struct (like the texture selector does) into a kernel-owned physically contiguous staging buffer; the zero-copy version maps the user buffer from `new_vertex_buffer` (already wired and GART-mapped) and takes its physical segments.
* **Handler steps**: lock `accel[0x544]`; validate count (multiple of 4, within the staging size); build chained descriptors (4092-byte stride, HOLD_OFFSET, EOL on the last); wait idle; save `BUS_CNTL`/`SRC_CNTL`/`BM_GUI_TABLE`; enable bus mastering, load `BM_GUI_TABLE_CMD`, set `SRC_CNTL`, kick; wait until `BM_GUI_TABLE == table_end && !GUI_ACTIVE` with a timeout; restore; unlock; return status.
* **Frame ordering**: the plugin sends state and the deferred clear in the frame's one PIO drain as today, then for each geometry chunk calls the DMA selector, then does the present drain. (Ordering of DMA vs. later PIO writes is guaranteed because the selector returns only after completion.)
* **Where the code goes** (open): needs room in the patched binary; the patch kit overwrites function bodies in place (`kext-patch/*.py`, MH_OBJECT, `file = vaddr + 0x33c`). The DMA handler is much larger than the 19-instruction memcpy. Candidates: bodies of other dead selectors, or extending `__text` in the object file (needs relocation handling, `gen_relocs.py` already does some).
* **Fallback**: no patched DMA selector (stock/older patched kext) -> today's PIO path with the cap.
* **Tests (MDD, headless)**: `heavy` probe at 1500 triangles reaches 0% missing; suite stays 183/183; soak; 2D fills concurrent with DMA frames; a deliberately bad address/count is refused with no hardware access.

## Open questions before writing kernel code
1. Code space in the stock binary (see above): how large can the handler be, and where does it live.
2. Staging memory in the kext: allocate a physically contiguous `IOBufferMemoryDescriptor` per accelerator (as Path A does, with `prepare()` and 16 KB-aligned ring), or take it from `new_vertex_buffer` buffers.
3. The kext's register access helper and delay/idle routines (`submit_buffer` internals at 0x12730, `accel[0x550]` register base) to reuse from hand-assembled code.
4. Interaction with Apple's own use of `BUS_CNTL`/`SRC_CNTL` (restore discipline) and with display sleep/wake.

## Static findings for the kernel handler (Nov 20, from the stock binary and a rebuilt patch chain; read-only)
* **The patch chain rebuilds from the stock binary** (`kext-patch/build-chain.sh`, md5 8fc97891...): patched/2/4/5/7 checksums match the author's; `patched8` adds the descriptor fix.
* **The sel-10 (`new_texture`) region is full**: 444 of its 484 bytes (0x71e4..0x73c8) are patched code (peek at 0x710c, multiplexed upload/alloc/AGP handler). No room for a DMA handler there.
* **Best code space: `IOATIRProGLContext::read_buffer` (selector 7, 0x6c50, 1056 bytes = 264 instructions).** The plugin never calls selector 7 (no use in `gldriver/` or `tools/`; the plugin reads VRAM through the CPU map). Smaller unused candidates: `get_surface_size` (148), `get_surface_info` (276), `get_status` (368). The methodDescs index order is set_surface 0, set_swap_rect 1, set_swap_interval 2, get_config 3, get_status 4, get_surface_size 5, get_surface_info 6, read_buffer 7, finish 8, wait_for_stamp 9, new_texture 10, delete_texture 11, become_global_shared 12, pageoff_texture 13, scale_surface 14. Replacing a selector's body also needs its in-region relocations neutralised, as `patch.py` does (the kext loader would otherwise rewrite them inside the new code).
* **Callable helpers are the compiler's long-branch "islands"** (`lis r12 / ori r12 / mtctr / bctr`, each relocated to an import). Near the GL-context code: `_memcpy` 0x6190, `IOBufferMemoryDescriptor::withOptions` 0x61a0, `_IOSleep` 0x6240, `_thread_block` 0x6250, `_mutex_unlock` 0x6260, `_mutex_lock` 0x6290; more at 0x7040/0x7060 (mutex), 0x12fb4 (`IOMemoryDescriptor::withPhysicalAddress`), `_IOLog` 0x28a0. There is no `IODelay`; waits use `IOSleep(1)` / `thread_block`. A `bl` has +-32 MB reach, so hand-written code can call any island.
* **Register access**: `accel[0x550]` is the register base (BAR + 0x400); `submit_buffer` (0x12730) does `stwbrx val, this[0x550], off`. Offsets below 0x400 wrap (reg - 0x400 negative), reaching block 0 (so `BM_GUI_TABLE` 0x1b8 etc. are addressed as `0x1b8 - 0x400`).
* **Lock**: `accel[0x544]` via `mutex_lock`/`mutex_unlock` islands (the patch-6/7 handlers already do this).

## Proposed build method
Write the handler in C, compile with the native gcc on the MDD (as the kexts are built), take the position-independent machine code, rewrite each call to a `bl` to the right island, and apply it over `read_buffer` with a new `patch8.py` (verify with the existing `verify-kext-patches.sh` approach and a capstone disassembly review before any load). Stages: (1) validate-only mode (all checks, no hardware access) on the MDD; (2) one tiny known stream (a flat triangle already used by `mach64_ringtest`); (3) the `heavy` probe. Each stage is reviewed (disassembly + trace of every pointer) before the live run.

## Kernel handler: built and verified (Nov 20)
**What exists** (`kext-patch/dma_handler.c`, `build-dma.sh`, `patch8.py`; output `ATIRagePro.patched9`): GL selector 7 (stock `read_buffer`, unused) is now a bus-master submit handler. Code lives in two regions whose old bodies nothing else branches into: R1 = [0x6b3c,0x7070) (get_surface_info + read_buffer, sels 6/7) and R2 = [0x6938,0x6aa8) (get_status, sel 4). Sels 4 and 6 now return kIOReturnUnsupported through a 3-instruction stub (the plugin does not use them; the research tools `mach64_surfscan`/`vramscan` call sel 6). The patch is built on the *installed* patched8 (`PATCH8_SRC=`), because the chain rebuilt from stock differs from it in two bytes of the peek handler (r2 vs r4 scratch register) and the installed binary is the one hardware has run all session.
**Interface** (`in` is a struct of u32 {op, arg, payload}; IOKit limits struct input to ~4 KB, so APPEND is chunked at <= 4088 payload bytes): op 0 reset, op 1 append register-write packets (kernel byte-swaps the data), op 2 submit (arg bit0 = dry run), op 7 self-test + state (magic, staging va, pa, staged bytes). Everything runs under `accel[0x544]`. Packets are validated before any hardware access (well-formed, <= 1024 values, exactly filling the stream, no write to BUS_CNTL, SRC_CNTL, BM_ADDR, BM_GUI_TABLE_CMD, BM_GUI_TABLE, BM_SYSTEM_TABLE and neighbours). The real run is Path A's `submitCommandBuffer` sequence unchanged (save BUS_CNTL/SRC_CNTL/BM_GUI_TABLE, wait FIFO empty + GUI idle, bus mastering on, table, SRC_CNTL, sync, kick DST_HEIGHT_WIDTH=0, wait BM_GUI_TABLE == table end and engine idle, restore).
**Measured facts found on the way**
* `IOMallocContiguous(size, 16 KB align)` aligns only the VIRTUAL address (va 0x309c4000 but pa 0x047bf000), so the handler over-allocates by 16 KB and aligns the physical address itself. (My first version refused such blocks as NOMEM; found by exposing the raw va/pa through op 7.)
* IOKit struct-input limit: an 8 KB input returns 0xfffffecd (MIG_ARRAY_TOO_LARGE). The plugin must append in <= 4 KB chunks, or a later revision maps a shared buffer.
**Verification so far**: stage 1 (no hardware) `tools/mach64_dmasel`: ALL PASSED (selftest, op validation, staging alloc, dry-run descriptor counts, refusals of truncated/overrunning packets and writes to BUS_CNTL/SRC_CNTL/BM_GUI_TABLE, 128 KB overflow refusal). Stage 2 (`mach64_dmasel hw`, a 16x16 2D solid fill streamed through the kernel handler into VRAM): 256/256 inside pixels correct and 768/768 outside untouched, 40 of 40 repeats pass; full `mach64_pathb_suite` on the patched9 kext: 183 passed, 0 failed (no regression of the PIO path).
**Not yet done**: plugin integration (emit geometry as DMA packets, chunked append, fallback when the selector answers kIOReturnUnsupported/BADARG), the heavy probe at 1500 triangles, concurrent 2D fill soak, bad-address tests with hardware, sleep/wake behaviour, and Lombard (G3, different memory map/bridge; the 4 GB physical limit check is the same).

## Plugin integration (Nov 20; DEFAULT ON since the user's decision, `MACH64_VDMA=0` disables) and results
`gld_render.c`: `vdma_avail()` detects the handler (sel 6 answers kIOReturnUnsupported 0xe00002c7 on patched9 but a cold-safe miss 0xe00002c2 on an unpatched kext; then an op-7 self-test) and `vdma_flush()` sends the batch (`p->batch`, no terminator, the kernel adds its own) as reset + <=1000-word appends + submit under a pthread mutex and the same `/var/tmp/mach64_dma.lock` flock the DMA texture upload uses. It is called from `mach64_draw_triangle` exactly where the plugin used to drop a triangle (batch = one PIO command buffer, ~8140 dw): the batch is drawn by DMA, a fresh batch starts and the render state is re-emitted. The end-of-frame submit stays on the PIO path because mapping type 1 is also the present. Frames below the old cap take the unchanged path.
**Measured (MDD G4, patched9):** heavy probe 1500 triangles/frame: baseline 79.3% missing (cap at #311); with VDMA 0 missing, 30/30 repeats; 3000 and 6000 triangles/frame 0 missing; two concurrent heavy processes (VDMA + DMA texture upload) both 0 missing; full suite with VDMA on 183/183.
**RESOLVED: the kernel panic was NOT the DMA path.** It was a dangling VRAM-heap record (surface backing at offset 0 never `heap_free`d on this headless rig) plus an ALLOC-failure path that returned an unlinked record; both fixed and verified, see `docs/re-notes/heap-offset0-dangling-record.md`. After the fixes: suite 183/183 (VDMA on and off), 150/150 heavy 1500-triangle DMA runs and 150/150 multictx runs without a notify between, 29 kill -9 mid-run, heap exhaustion handled.

**Default (Nov 20, user decision: DMA is not opt-in).** Both the vertex-DMA overflow flush and the DMA texture upload are on unless `MACH64_VDMA=0` / `MACH64_DMA_UPLOAD=0`. Both fall back silently when their kernel side is absent (unpatched kext / no Path A kext). Verified with no environment set: suite 183/183 (and 183/183 with both off), heavy 1500 = 0 missing, 60 x (heavy 3000 + multictx/tex_mip/dmaupload) clean, heap list intact. The patched ATIRagePro (patched9) and `stubctl notify` (offset-0 guard) are REQUIRED for the default to be safe; the install procedure must ship both.
